# ARM STUDIO — 로봇 제어와 AI 기술 문서

로봇팔이 어떻게 움직이고, AI가 어디까지 관여하며, 그 둘이 어떻게 만나는지의 기록.
읽는 순서는 위에서 아래로, 사람의 말이 로봇의 움직임이 되는 순서와 같다.

---

## 0. 전체 그림

```
사람의 말
   │
   ├── [Whisper]  음성 → 한국어 텍스트                     (AI)
   │
   ├── [hints]    문장 속 색·번호 → 도킹 id                (계산)
   │
   ├── [RACHEL]   텍스트 → 블록 목록                       (AI)
   │
   ├── [검증]     id 확인 · 이동 보장 · 없는 대상 폐기      (계산)
   │
   ├── [기구학]   블록 → 관절각 경로                       (계산)
   │      FK · IK · 수평 구속 · 도달 판정 · 충돌검사
   │
   ├── [3D 뷰어]  이론 자세로 미리보기                     (계산)
   │
   └── [모터]     보정 자세로 실물 전송                    (계산)
```

**AI는 두 곳에만 있다.** 음성을 글자로 바꾸는 곳과, 글자를 블록으로 바꾸는 곳.
그 사이와 그 뒤는 전부 결정론적 계산이다. 같은 블록은 언제나 같은 관절각을 낸다.

이 경계선은 취향이 아니라 안전 설계다. 로봇은 틀리면 물건이 깨지고 사람이 다친다.
"대체로 맞는" 답을 내는 부품을 제어 경로에 두지 않는다.

## 1. 로봇 하드웨어

### 1-1. 레퍼런스 기체

| 항목 | 값 |
|---|---|
| 기체 | SO-ARM101 (6축) |
| 서보 | Feetech STS3215 × 6 (ID 1~6) |
| 통신 | 시리얼 1 Mbps, 데이지체인 |
| 연결 | USB 시리얼 어댑터 (`/dev/serial/by-id/...`) — 자동 인식 |
| 그리퍼 | j6 (마지막 축) |

Dynamixel(XC/XM430, Protocol 2.0) 로봇도 같은 UI로 제어할 수 있고,
UR15는 시뮬레이션 전용으로 등록되어 있다.

### 1-2. 관절 축 구성 — 모든 제어 규칙의 출발점

```
j1  (0,0,1)  Z축 회전   →  팔 전체를 좌우로 돌린다. 기울기와 무관
j2  (1,0,0)  X축 회전   ┐
j3  (1,0,0)  X축 회전   ├  세 축이 평행하다 → 세 각의 합이 그리퍼 기울기
j4  (1,0,0)  X축 회전   ┘
j5  (0,1,0)  Y축 회전   →  돌리면 무조건 기운다
j6           그리퍼     →  열기/닫기 전용
```

j2·j3·j4가 같은 축을 공유한다는 사실이 이 시스템 전체를 규정한다.
아래 3-2에서 이어진다.

### 1-3. 모터 파라미터 (실측 튜닝값)

| 상수 | 값 | 의미 |
|---|---|---|
| `BAUD` | 1,000,000 | 시리얼 속도 |
| `GAIN_KP/KD/KI` | 64 / 64 / 4 | 위치 PID. 공장값 32/32/0은 이 팔에 약했다 |
| `SAFE_VEL` | 150 | 이동 속도 상한 |
| `SAFE_ACCEL` | 8 | 가속. 높이면 덜덜 떨린다 |
| `TORQUE_LIMIT` | 250 | 토크 상한 |
| `DEADZONE` | 10 카운트 | 실측 모터 데드존 |
| `END_TOL` | 6 raw | 도착 판정 허용치 ≈ 0.53° ≈ 엔드이펙터 3mm |

**게인 튜닝 결과**

```
Kp32 / Kd32 / Ki0  →  정지 오차 18 raw (1.58°)   공장 기본값
Kp64 / Kd64 / Ki4  →  정지 오차  4 raw (0.35°)   채택
```

중력 때문에 남는 정상편차는 적분항(Ki)이 지운다. Ki를 0으로 두면 팔이
목표 아래에서 멈춘 채 버틴다.

### 1-4. 안전장치

- **관절 한계를 모터 EEPROM에 기록한다.** 소프트웨어가 죽어도 모터가 스스로
  그 범위를 벗어나지 않는다. SW 한계 검사는 그 위에 한 겹 더 있는 것이다.
- **정지 = 즉시 토크 해제.** 감속이 아니라 힘을 끊는다.
- **로봇 불일치 차단.** 3D에서 UR15(8축)를 고른 채 실물 전송을 시도하면
  `real_robot_ok()`가 막는다. 8축 각도가 6축 모터에 들어가면 팔이 부러진다.
- **AI는 관절값 생성 권한이 없다.** LLM이 만들 수 있는 것은 블록 목록뿐이고,
  블록이 관절각으로 번역되는 경로에는 AI가 없다.

## 2. 좌표계와 툴 중심

### 2-1. cr_7 (툴 중심)

로봇이 "어디에 있는가"를 말할 때 기준이 되는 점이다. j6 링크에서
`[-9, 39.5, 39.3] mm` 떨어진 위치로, 사용자가 SolidWorks에서 그리퍼 회전 원의
중심에 잡은 좌표계다. URDF에서 계산되며 하드코딩이 아니다.

주의할 점이 하나 있다. `axis_7`은 **움직이는 죠(jaw)** 링크에 붙어 있어서
그리퍼를 열면 실제 위치가 바뀐다. 그러면 같은 자세인데 좌표가 달라 보인다.
그래서 툴 중심을 평가할 때는 j6를 기준각(`J6_TOOL_REF`)으로 고정한 상태로
계산한다 — 그리퍼가 열려 있든 닫혀 있든 같은 좌표가 나온다.

### 2-2. 잡는 높이 — 고정식

도킹 스테이션에 결합할 때의 높이는 매번 계산하지 않고 실측 고정값을 쓴다.

```
115 mm   도킹 스테이션 높이
+ 10 mm  도킹 윗면 → 그리퍼가 닿는 면   (GRASP_FACE_DZ)
+ 37 mm  잡는 면 → cr_7 중심            (GRASP_DZ_DEFAULT, 실측 36.67)
────────
= 162 mm  바닥 기준 잡는 점
```

계산으로 매번 구하면 메쉬 오차가 누적되고, 도킹 종류가 바뀔 때마다 값이
흔들린다. 실측 한 번으로 고정하는 편이 정확하고 재현된다.

## 3. 기구학 — 계산 영역의 핵심

### 3-1. 순기구학 (FK)

URDF를 파싱해 관절 체인을 만들고, 각 관절의 동차변환 행렬을 순서대로 곱해
엔드이펙터 위치를 얻는다. 로봇이 바뀌면 URDF만 바꾸면 된다 — 축 개수와
링크 길이를 코드에 적어두지 않는다.

### 3-2. 수평 구속 — 이 시스템의 정체성

**문제.** 일반적인 IK 솔버는 목표 지점에 도달하기만 하면 중간 자세는 신경쓰지
않는다. 하지만 물건을 나르는 로봇에게는 경로 전체에서 그리퍼가 수평을
유지하는 것이 도달 정확도만큼 중요하다. 기울면 물건이 미끄러지거나 쏟아진다.

**해법.** 1-2에서 본 대로 j2·j3·j4는 같은 축을 공유한다. 따라서

```
그리퍼 기울기 = j2 + j3 + j4  (세 각의 합)
```

이 합을 경로 전 구간에서 상수로 유지하고, j5는 아예 잠근다. j5는 Y축이라
조금만 돌려도 무조건 기울기 때문에 오프셋 자체를 금지한다.

**구현에서 지켜야 하는 것들**

- 세 관절을 **한 묶음으로 보간**한다. 하나씩 순서대로 돌리면 중간에 합이 깨진다.
- 축마다 이동량이 다르면 **속도를 맞춰 동시에 도착**시킨다. j2가 먼저 도착하고
  j3가 나중에 도착하면 그 사이에 합이 달라진다.
- **미세조정 보정도 같은 구속을 지킨다.** 사용자가 j3에 +5°를 주면 j4가 자동으로
  −5°를 받는다 (`level_offset`). 보정 때문에 수평이 깨지는 일이 없다.
- 제공하는 이동 모드 5종에 **전부** 수평유지가 걸려 있다. 예외가 없다.

```
관절 순서대로 (수평유지)
관절 동시 (수평유지)
EE 직선 (수평유지)
EE 축별 이동 (수평유지)
EE 축별 · 자세까지 수평보정
```

8축(UR15 등)에서는 관절 구성이 다르므로 `axis_end` 수평 유지로 일반화한다.
허용 오차 4°, 실측 최대 1.07°.

### 3-3. 역기구학 (IK) — 목적별 3종

시드 기반 반복 최적화로 직접 구현했다. 현재 자세 근방의 시드 여러 개에서
출발해 수렴시키고, 관절 한계 안에서 목표 오차가 가장 작은 해를 고른다.

| 함수 | 용도 |
|---|---|
| `ik_general` | 일반 6축. 자유도 제한 없음 |
| `ik_tool` | 툴 중심(cr_7) 기준. j5·j6를 고정해 평가 |
| `ik_level` | 수평 구속. **j5·j6를 변수에서 제외한 4축 체인** |

`ik_level`이 중요하다. 솔버에게 j5를 주지 않으면 솔버가 j5를 건드릴 수 없고,
따라서 수평이 깨질 가능성이 원천적으로 사라진다. 제약을 거는 것보다
자유도를 없애는 편이 확실하다.

### 3-4. 간편 이동 — 뽑기 → 수평 → 하강

물건을 A에서 B로 옮기는 기본 동작은 3구간으로 나뉜다.

```
① 뽑기    현재 x,y를 유지한 채 도달 가능한 최대 z까지 수직 상승
② 수평    그 높이를 유지한 채 목표 x,y로 이동 (x 먼저 또는 y 먼저)
③ 하강    목표 x,y에서 수직 하강
```

수직으로 뽑고 수직으로 내리므로 도킹 소켓에서 물건이 걸리지 않는다.
②에서 충돌이 예상되면 우회 높이를 올리고 경로에 경고를 남긴다.

### 3-5. 도달표 — 미리 계산해 두는 것

**목심 도달표** (658칸): 격자점마다 도달 가능 여부와 자세를 미리 계산해 저장.
**조종표** (143,667칸, 10mm 격자): 조그 이동용. 시작 시 0.7초에 로드.

핵심은 **로봇 상대좌표로 저장**한다는 것이다. 월드좌표로 저장하면 로봇이나
설비를 옮길 때마다 전부 다시 계산해야 한다. 상대좌표면 로봇이 어디로 가든
표가 그대로 유효하다 — **재배치 시 재계산 0초.**

도달상한(`maxz`) 캐시는 ①뽑기 구간의 높이 계산을 가속한다.

### 3-6. 충돌검사

trimesh로 메쉬를 다루고 fcl로 경로를 사전 검증한다. 설비 STL과 로봇 링크
메쉬를 모두 등록해, 계획된 경로가 실제로 통과 가능한지 실행 전에 확인한다.

## 4. 모션 실행 — 진동과의 싸움

이 절은 실패의 기록이기도 하다.

### 4-1. 결론: 단순한 쪽이 이겼다

```python
for f in waypoints:
    sync_speed(prev, f, dt)   # 축별 속도를 맞춰 동시 도착
    send(f)                   # 목표 각도 전송
    sleep(dt)                 # 시간만큼 기다림
    prev = f
```

이것이 전부다. 도착 확인도, 오차 재측정도, 재보정도 없다.

### 4-2. 무엇을 뺐고 왜 뺐나

**이동 중 모터 읽기 제거.** `ROBOT.read()`는 모터 6개를 하나씩 조회하므로
250ms가 걸린다. 걸음마다 읽으면 그 250ms 동안 팔이 멈춘다 — 끊김의 정체가
이것이었다. 3D 화면은 직전 목표(`CURRENT_Q`)를 이미 알고 있으므로 읽을 이유가 없다.

**settle(도착 확인 + 과보정) 제거.** 목표에 도달했는지 확인하고 오차만큼 다시
밀어넣는 로직이 있었다. 이것이 진동의 근원이었다. 모터는 이미 목표를 향해
가고 있는데 외부에서 목표를 흔들면 헌팅이 생긴다. `SETTLE_ON=[False]`로
끄고 구형 방식(보내고 쉬기)으로 돌아갔더니 진동이 사라졌다.

**교훈.** 폐루프가 항상 옳은 것은 아니다. 서보가 이미 내부에서 폐루프를
돌리고 있다면, 그 위에 또 한 겹을 얹는 것은 간섭이다.

### 4-3. 그리퍼 — 여기만 폐루프

그리퍼는 예외적으로 위치를 읽는다. 이유가 분명하다.

```
닫힘 완료까지 실측 3.2초.
안 기다리고 팔을 올리면 덜 닫힌 채 상승해서 물건을 놓친다.
```

**파지 감지**: 닫는 중 위치가 4틱 연속 멈추면(변화 < 8) 물체를 잡은 것으로
판정하고, 목표를 현재값보다 25 낮춘 지점으로 재설정해 살짝만 조인다.
끝까지 조이면 과부하 보호가 걸려 토크가 끊긴다.

**열기 재시도**: 1.2초 동안 움직이지 않으면 이전 파지로 보호가 걸린 것이므로,
토크를 껐다 켜서 보호를 해제하고 토크를 올려 다시 시도한다.

**시뮬레이션에서는 이 대기를 전부 건너뛴다.** 읽을 모터가 없는데 기다리면
8초 타임아웃을 꽉 채운다 — 잡기+놓기 한 번에 32.8초가 낭비됐다.

### 4-4. 보정값의 분리

```
3D 화면  ←  이론 자세 (URDF가 말하는 정답)
실물 모터 ←  이론 자세 + 보정값 (조립 오차·링크 휨을 메운 값)
```

보정값은 **자세마다, 로봇마다** 따로 저장한다(`sts`/`dxl`). 같은 자세라도
로봇이 다르면 조립 오차가 다르기 때문이다.

시뮬레이션은 보정값을 쓰지 않는다. 3D에는 실물의 조립 오차가 없으므로,
보정을 적용하면 화면이 오히려 틀린 자리로 간다.

## 5. 블록 파이프라인

### 5-1. 블록 6종

| 블록 | 동작 | 좌표 |
|---|---|---|
| 이동 → 대상 | 뽑기 → 수평 → 하강 | **있음** |
| 잡기 | 열기 → 하강 → 닫기 → 상승 | 없음 |
| 놓기 | 하강 → 열기 → 상승 → 닫기 | 없음 |
| 그리퍼 열기/닫기 | 제자리 | 없음 |
| 하강 / 상승 | 제자리 수직 | 없음 |

### 5-2. 좌표는 이동 블록만 갖는다

**잡기와 놓기는 좌표를 갖지 않는다.** 지금 서 있는 자리에서 수직으로만
움직이고, 높이만 대상에서 얻는다.

이유가 있다. 예전에는 잡기가 스스로 대상의 XY를 계산했는데, 그러면 이동
블록이 계산한 XY와 잡기가 계산한 XY가 **두 개**가 된다. 두 계산이 조금이라도
다르면 어긋난다 — 실측 23mm 차이가 났다. 좌표를 갖는 블록을 하나로 못박으면
이 문제가 원천적으로 사라진다.

그래서 잡기·놓기 앞에는 반드시 해당 대상으로 가는 이동 블록이 있어야 하고,
없으면 `seq_fix_moves()`가 자동으로 넣는다.

### 5-3. 이동 블록은 실행 시점에 재계산한다

미리 계산한 경로를 쓰면, 파이프라인 중간에 물체가 옮겨졌을 때 옛 위치로
가버린다. 그래서 이동 블록은 실행하는 순간 대상의 현재 위치로 경로를 다시 푼다.

단, 사용자가 미세조정해 **등록해 둔 자세**가 있으면 그것을 우선한다.
보정한 각도가 정답이기 때문이다. (시뮬레이션에서는 4-4의 이유로 제외)

## 6. AI — 어디까지 관여하는가

### 6-1. 음성 인식

whisper.cpp, large-v3-turbo, 한국어. DGX Spark에 상주하고 터널로 연결한다.

whisper 서버는 스트리밍을 지원하지 않는다. 그래서 "지금까지 녹음한 것"을
1초마다 통째로 다시 보내 자막을 갱신한다 — 진짜 스트리밍은 아니지만 보기에는
같다. 실행은 버튼을 다시 눌렀을 때 전체를 다시 변환해서 한다.

브라우저 내장 음성 인식은 말 중간의 뜸에서 스스로 끊기므로 폴백으로만 쓴다.

### 6-2. 언어 모델 — 세 가지 중 선택

UI(②시뮬레이션 탭)에서 고를 수 있다.

| 선택 | 모델 | 위치 | 특징 |
|---|---|---|---|
| 자동 | Gemma → 규칙 | Spark | 서버 되면 Gemma, 아니면 규칙 |
| **RACHEL** | 자작 10M | **앱 내장** | 서버 불필요, CPU 2초 |
| Gemma 4 | E4B 파인튜닝 | Spark | GPU 68 tok/s |
| 규칙 파서 | — | 앱 내장 | AI 완전 배제 |

**RACHEL**은 이 프로젝트에서 밑바닥부터 만든 전용 소형 언어 모델이다
(구조·토크나이저·데이터·학습 전부). 상세는 `nano_llm/TRAINING.md`.

**Gemma 4 E4B**는 llama.cpp로 서빙한다. 주의할 점 하나: 이 모델은 답하기 전에
길게 생각하고 그 내용을 `reasoning_content`에 담는데, 복잡한 명령에서
생각만 하다 토큰을 소진해 `content`가 빈 문자열로 돌아온다. 프롬프트로
"생각하지 마라"라고 해도 통하지 않는다. `chat_template_kwargs:
{enable_thinking: false}`만 듣는다. (실측: 사고 켬 14.2초·블록 0개 →
사고 끔 4.2초·블록 8개)

### 6-3. AI가 하지 않는 일 — 힌트 전처리

색을 도킹 id로 바꾸는 것은 사전 찾기다. 계산이 완벽하게 할 수 있는 일을
신경망에 시킬 이유가 없다.

```
장면:  보라=d2 빨강=d10 주황=d11
문장:  "보라색 펜을 빨간 데로 옮겨"
힌트:  d2 d10        ← hints.build() 가 만든다 (20줄, 정규식)
```

RACHEL에게 남는 일은 "어느 것이 출발지이고 어느 것이 도착지인가"라는
**언어 구조 판단**뿐이다. 이 분리 하나로 색 지칭 정확도가 64% → 99.6%로 올랐다.
같은 모델, 같은 데이터에서 경계선만 옮긴 결과다.

### 6-4. AI 출력 검증 계층

LLM이 낸 답을 그대로 믿지 않는다. 실제로 관찰된 오류들과 그 대책이다.

| 관찰된 오류 | 대책 |
|---|---|
| id에 설명까지 복사 (`@grasp:ppap (색:초록…)`) | 괄호 앞까지 잘라 재매칭 |
| blocks를 이중 포장 (`[{"blocks":[…]}]`) | 재귀적으로 평탄화 |
| 번호만 씀 (`@goto:7`) | 별명표에 맨 숫자도 등록 |
| 잡기 앞에 이동 블록 누락 | 후처리로 강제 삽입 |
| 장면에 없는 대상 | 블록 폐기 후 되물음 |
| JSON 형식 깨짐 (글자 단위 생성 부작용) | 정규식으로 @블록만 복구 |

마지막 항목이 상징적이다. RACHEL이 `{"blocks"@goto:d2", …}`처럼 형식을
깨뜨려도, **내용은 맞다.** 형식 수리는 계산이 하면 된다.

### 6-5. 폴백 사슬

```
RACHEL / Gemma  →  실패  →  규칙 파서  →  실패  →  "무슨 뜻인지 모르겠습니다"
```

어느 단계가 죽어도 앱은 멈추지 않는다. Spark 연결이 끊기면 30초마다
자동으로 다시 찾고, 그동안에는 규칙 파서가 받는다. 인터넷 없이도 기본
명령은 동작한다.

## 7. 디지털 트윈

### 7-1. 구조

three.js 뷰어가 별도 포트(7870)에서 돌고, 앱(7900)이 애니메이션 청크를 보낸다.
같은 파이프라인이 3D와 실물 양쪽으로 나가므로 화면과 실물이 어긋나지 않는다.

### 7-2. 전송 최적화

청크를 JSON으로 보내던 것을 바이너리로 바꿨다.

```
4.1 MB JSON  →  1.1 MB 바이너리
2,825 ms     →  6 ms
```

헤더(int32) + 시간축(float64) + 키(int16) + 값(float32)을 그대로 이어붙인다.
포트가 다르므로 CORS 헤더가 필요하다 — 이것이 없어서 브라우저가 요청을
조용히 막고 있었고, 원인 파악에 오래 걸렸다.

### 7-3. 공장 배치

설비 STL을 드래그해서 배치한다. 끌고 오면 실물 모양이 커서를 따라오고,
다리(핀) 2개를 목심에 클릭해 자리와 회전을 확정한다. 물체는 항상 도킹
스테이션 위에 올라간다(중심축 일치, 바닥 = 도킹 윗면).

도킹은 배치 순서대로 색과 번호를 고정 배정한다 — 빨강 #8, 주황 #9, 노랑 #12.
지우고 다시 깔아도 같은 색이면 같은 번호를 받는다. 발표 자료와 화면이
어긋나지 않게 하기 위한 장치다.

## 10. 설계 원칙 요약

1. **AI는 해석에만, 제어는 계산에.** 틀리면 안 되는 것을 확률적 부품에 맡기지 않는다.
2. **자유도를 없애는 것이 제약을 거는 것보다 확실하다.** (ik_level의 4축 체인)
3. **좌표를 갖는 주체는 하나여야 한다.** 둘이면 반드시 어긋난다.
4. **폐루프가 항상 옳지는 않다.** 서보가 이미 돌리는 루프 위에 얹으면 간섭이다.
5. **미리 계산할 수 있으면 미리 한다.** 단, 재사용 가능한 좌표계로 저장한다.
6. **모든 계층에 폴백을 둔다.** 어느 하나가 죽어도 시스템은 멈추지 않는다.
