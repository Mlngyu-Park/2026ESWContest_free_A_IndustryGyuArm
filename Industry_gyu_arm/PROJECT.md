## 2. DUSK — 완전 정수화

### 무엇을 했나

RACHEL 을 **실수 연산 0줄**로 다시 썼다.
`double` · `pow` · `exp` · `sqrt` · `tanh` 가 추론 경로에 하나도 없다.

**왜?** 68000 같은 옛 CPU 에는 부동소수점 유닛이 없다.
실수를 쓰면 소프트웨어 에뮬레이션이라 수십 배 느려진다.

### 잡은 버그 11개

대부분 **int32/int64 오버플로**였다. 기억할 만한 것:

| 증상 | 원인 | 해결 |
|---|---|---|
| 긴 답의 37~93번째 글자만 틀림 | KV 캐시에 그 시점 스케일 미저장 | 위치별 스케일 저장 → 91%→100% |
| LayerNorm 바꾼 순간 0% | 정수 변환 순서 | 하나씩 바꾸며 200문장 재검증 |

**교훈:** 커널 하나씩은 맞는데 **8층을 거치면 어긋난다.**
단위 시험만으로는 못 잡는다.

### 핵심 커널

```c
int32_t dusk_mac_row(const int8_t *w, const q15_t *x, int n)
{
    int64_t acc = 0;
    for (int i = 0; i < n; i++)
        acc += (int64_t)w[i] * (int32_t)x[i];
    /* int32 로 클램프 */
}
```

## 3. 실제 하드웨어에서 검증한 것

### Arduino Due (ARM Cortex-M3, 84MHz) 실측

**노트북을 저장장치로, Due 를 계산 노드로** 쓰는 구조를 만들어 돌렸다.
가중치 9.4MB 는 노트북에 두고, Due 에게 행렬곱만 시켰다.

| 확인한 것 | 결과 |
|---|---|
| 320 MAC 비트 단위 일치 | **25124287** (0x017F5DBF) 정확히 일치 |
| 실제 가중치 64행 | **전부 비트 단위 일치** |
| 커널 최적화 | **1.6배** (13.4 → 8.4 사이클/MAC) |
| 속도 | 약 **9.95 M MAC/s** |

### 커널 최적화의 정체

```c
/* 느림: 매 항마다 int64 누산 — 13.4 사이클/MAC */
acc64 += (int64_t)w[i] * x[i];

/* 빠름: int32 로 16개 모으고 한 번만 int64 — 8.4 사이클/MAC */
acc32 = w[i]*x[i] + w[i+1]*x[i+1] + ... (16개);
acc64 += acc32;
```

**안전성:** 16 × 127 × 32767 = 6,657만 < int32 한계 21억. **32배 여유.**

### 겪은 실패

**128행에서 USB 타임아웃.** 160KB 를 한 번에 밀어넣으니 Due 가
받는 속도를 앞질러 버퍼가 넘쳤다.
→ **행마다 ACK** 를 주고받는 흐름 제어로 해결.

## 4. 통신 병목 — 32노드가 1노드보다 느리다

가장 중요한 발견이다.

| 방식 | 계산 | 통신 | 합계 | 가속 |
|---|---|---|---|---|
| 단일 칩 | 14.2초 | 0 | 14.2초 | 1.0배 |
| **행 분할 32노드** | 0.44초 | **70.2초** | 70.7초 | **0.20배** |
| 층 분할 8노드 | 1.77초 | 1.1초 | 2.8초 | 5.0배 |

**32개가 1개보다 5배 느리다.**

행 분할은 토큰당 640KB, 문장당 81MB 를 뿌리고 모은다.
동기화만 4,160회다. 노드를 늘릴수록 통신이 폭발한다.

### 그래서 TPU 로 간다

```
클러스터:  노드0 계산 → 결과를 링에 실어 → 노드1 이 받음
           ↑ 전선 수십 cm, 프로토콜, 버퍼, 대기

시스톨릭:  칸(0,0) → 부분합을 바로 아래 칸(1,0) 으로
           ↑ 배선 한 가닥, 클럭 하나에 이동
```

**TPU 는 통신을 배선으로 바꾼다.** 노드를 늘려도 병목이 안 생긴다.

## 5. 자작 TPU 설계

### PE 하나가 하는 일

```
      x_in
       ↓
   ┌─────────────────────────┐
 x→│  w (래치에 고정)          │→ x_out    x 는 오른쪽으로
   │  psum_in + w*x = psum    │
   └──────────┬──────────────┘
              ↓ psum_out                  부분합은 아래로
```

프로그램 카운터도 명령 해석기도 없다. **이게 CPU 와의 근본 차이다.**

### 핵심 아이디어 — 곱셈을 ROM 으로

74HC 로 8×8 곱셈 회로를 짜면 칩이 **15~20개** 든다.
**룩업 테이블을 쓰면 메모리 하나면 된다.**

```
주소  A0~A7  = x (활성값)
      A8~A15 = w (가중치)
      A16    = 곱의 하위/상위 바이트
출력  D0~D7  = 결과 바이트
```

`mul_lut.bin` (128KB) 을 만들었고 **65,536 조합 전수 검증 완료**.

### PE 하나 = 칩 9개

| 칩 | 개수 | 역할 |
|---|---|---|
| SST39SF040 | 1 | 곱셈 룩업표 |
| 74HC574 | 4 | w래치 · x래치 · psum하위 · psum상위 |
| 74HC283 | 4 | 16비트 가산기 (4비트 × 4) |

### 클럭이 전부를 정한다

```
74HC574 clk→out  25ns
+ 플래시 읽기     70ns
+ 74HC283 캐리    60ns
+ setup          15ns
─────────────────────
= 170ns → 최대 5.9MHz
```

| 실측 클럭 | 5초 달성에 필요한 PE |
|---|---|
| 30 MHz | 9 |
| 20 MHz | 13 |
| 15 MHz | 18 |
| 9.5 MHz | 27 |
| 5.9 MHz | 43 |

**이 숫자를 재는 것이 PE 2개 시제품의 목적이다.**

## 6. PE 2개 시제품 — 지금 만드는 것

### 왜 2개인가

1개로는 "곱하고 더한다"만 확인된다.
**2개를 붙여야 시스톨릭의 핵심 — 데이터가 이웃으로 흐르는 것 — 을 본다.**

```
   x → [PE0] → [PE1] → x_out
        ↓       ↓
      psum0   psum1
```

### 확인할 것 다섯

1. 곱셈 LUT 가 맞는 값을 내는가
2. 누산이 제대로 되는가
3. x 가 한 클럭에 정확히 한 칸 이동하는가
4. **최대 클럭이 몇 MHz 인가** ← 핵심
5. 두 PE 사이 클럭 스큐가 문제없는가

### 규모

| 항목 | 값 |
|---|---|
| 칩 | 20개 |
| 신호선 | 157가닥 |
| 전원선 | 40가닥 |
| **납땜 지점** | **약 394곳** |
| 기판 | 55×49 구멍 ≈ 140×124mm |

### 핀 배치 — 전부 데이터시트로 검증함

| 칩 | 출처 | 상태 |
|---|---|---|
| SST39SF010A/040 | Microchip **DS20005022F** p.3 | ✅ |
| 74HC283 | Philips Rev.03 p.4 | ✅ |
| 74HC574 | Nexperia Rev.10 p.3 | ✅ |
| 74HC74 | Nexperia Rev.9 p.3 | ✅ **오류 발견→수정** |

**74HC74 에서 실제 오류를 잡았다.** 2번 플립플롭의 핀이
1번과 거울처럼 반대였다 (1번은 D=2·CP=3, **2번은 CP=11·D=12**).
그대로 납땜했으면 클럭 분주가 아예 안 돌았다.

### 만든 도구

| 파일 | 내용 |
|---|---|
| `tpu_pe/layout.py` | 배치도·배선도 자동 생성 + **자체 검증** |
| `tpu_pe/layout.png` | 만능기판 배치도 (색깔별 배선) |
| `tpu_pe/배선목록.txt` | 197가닥 납땜 체크리스트 |
| `tpu_pe/pe2.net` | VeroRoute 넷리스트 (Protel1/Tango) |
| `tpu_pe/WIRING.md` | 핀 번호까지 나온 배선표 |
| `tpu_pe/mul_lut.bin` | 곱셈 룩업표 128KB |

`layout.py` 는 칩 겹침·핀 이름 오류·입력 충돌·주소선 누락을
**스스로 검사한다.** 실제로 칩 겹침 4곳을 잡아냈다.

## 10. SOL — 납땜 설계 언어·검증기·3D 뷰어 (2026-09-16 밤)

`sol/` 폴더. 회로를 `.txt` 로 적고(`pin REF[핀:넷]` 포인터 표기),
프로그램이 **데이터시트 숫자만으로** 검증하고, 3D/2D 로 보고, KiCad 로 넘긴다.

```
gen_pe2.py (AI 가 배선, 연결만)  →  pe2.txt
sol.py (검증 R1~R12 + 타이밍)     →  pe2.json / pe2.kicad.net / 체크리스트
build_viewer.py                   →  viewer.html (GPU 없이 Canvas 2D)
tpu.py                            →  보유 부품으로 가능한 PE, 임계경로, 대안
```

**원칙:** AI 는 전압·시간을 적지 않는다. 검증기는 AI 의도를 모른다.
둘이 다르면 데이터시트를 연다.

**검증기가 잡은 것:**

| 발견 | 조치 |
|---|---|
| 플래시 DQ **VOH(min) 2.4V < 74HC283 VIH 3.15V** — 규격상 HIGH 보장 안 됨 | 가산기 → **74HCT283** (VIH 2.0V, 같은 핀). 산 74HC283 은 규격 밖 |
| 74HC283 캐리 지연 실제 max **39~46ns** (내가 22ns 로 잘못 앎) | 임계경로 **222ns → 4.5MHz** 로 정정 |
| 옛 배선에 74HC244 가 안 붙어 있었음 (플로팅 16개) | 클럭 버퍼로 실제 배선 |

**tpu.py 결론 (보유 부품, 데이터시트 max):** PE 2개 · 4.5MHz · 토큰 1.1초 · 문장 145초.
파이프라인(574 +4/PE)이면 8.7MHz. 5초/문장엔 PE 31~53개.
