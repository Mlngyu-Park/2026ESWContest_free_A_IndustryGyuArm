# 인수인계 — RACHEL 을 옛날 CPU 에서 돌리기

**목표: 자작 언어모델 RACHEL 을 낡은 CPU 여러 개로 실제로 돌린다.**

68000 전용이 아니다. **칩을 바꿔 끼울 수 있는 형태**로 만드는 것이
목적이다. 68000 으로 먼저 하고, 나중에 다른 칩(6502·Z80·68020·486…)도
같은 코드로 시험한다.

---

## 사용자에 대해

- **박민규**, 2026 임베디드SW경진대회(자유공모 A형)
- **존댓말**을 쓰고, 전문용어는 풀어서 설명할 것. 한국어로 대화한다
- 이미 RACHEL 을 from scratch 로 만들어 봤다 — 기초 설명 불필요

### 반드시 지킬 것 (사용자가 직접 요구한 것)

- **사용자 PC 에서 무거운 연산 돌리지 말 것.** GPU 는 다른 데 써야 한다.
  회의 중 팬 소리 때문에 곤란했던 적이 있다. 무거운 건 DGX Spark 에서.
- **`start_pro.sh` 는 절대 건드리지 말 것.** 명시적으로 금지했다.
- 실행 중인 프로그램을 함부로 끄지 말 것
- 보안·네트워크·타 기기 작업은 **먼저 물어보고**
- 모르는 건 추측하지 말고 질문할 것
- **수치를 지어내지 말 것.** 실측하거나, 계산이면 계산이라고 밝힐 것

## 지금까지 만들어 둔 것

### 1. RACHEL — 돌릴 모델 (완성)

**파인튜닝이 아니라 랜덤 가중치에서 시작한 from scratch 모델이다.**

| 항목 | 값 |
|---|---|
| 하는 일 | 한국어 말 → 로봇 블록 JSON |
| 파라미터 | 10,053,120 (10.1M) |
| 구조 | GPT 디코더 · d320 L8 H8 · 문맥 256 |
| 어휘 | 글자 단위 167자 |
| 정확도 | 200/200 = 100% (C++), 학습 검증 99.6% |
| 가중치 | int8 **10.1MB** (`rachel_cpp/rachel.bin`, RCHL 형식) |
| 현재 속도 | 노트북 C++ 168ms |

만든 과정: `nano_llm/MAKING_RACHEL.md`, `nano_llm/TRAINING.md`

### 2. C++ 추론 엔진 (완성, 이식의 원본)

`rachel_cpp/rachel.cpp` — **307줄, 외부 라이브러리 없음.**
이걸 어셈블리나 C 로 옮기면 된다. 구조가 단순해서 이식이 현실적이다.

- KV 캐시 있음 (토큰마다 전체 재계산 안 함)
- W8A32: 가중치 int8, 활성값 float32
  → **CPU 이식 때는 활성값을 int16 고정소수점으로 바꿔야 한다** (아래 참조)

### 3. 68000 어레이 설계 (문서만, 하드웨어 없음)

- `DESIGN.md` — 칩 선정 근거, 메시지 패싱 링, 예산 약 74만원
- `mac_68k.s` — 68000 MAC 커널 (MULS 기반, 실측 108T/MAC)
- `emulate.py` — 32노드 에뮬레이터 (`--clk`, `--nodes`, `--topo`)

**`emulate.py` 를 먼저 읽을 것. 생각보다 많이 돼 있다:**

| 이미 구현된 것 | 함수 |
|---|---|
| 정수 전용 MAC (float 없음) | `mac_int()` — MULS+ADD.L 을 정수로 |
| 활성값 int16 양자화 | `quant_act()` — 68000 에 float 가 없어서 |
| **행 분할** (32노드) | `matvec_array()` — 워커 k 가 i≡k(mod 32) 행 담당 |
| 가장 느린 노드 추적 | `stats['peak']` — 시간을 결정하는 값 |
| 통신량 계산 | `stats['bytes']` — 입력 뿌리기 + 결과 모으기 |
| LayerNorm·GELU 정수판 | `layernorm()`, `gelu()` |

즉 **1~2단계의 상당 부분이 이미 끝나 있다.** 처음부터 짜지 말 것.

### 4. 68000 3D 렌더러 (완성, 참고용)

`m68k_array/gfx/pl68k.c` — 공장 3D 를 68000 사이클로 그린다.
**여기서 이미 검증된 것이 있다:**

- 화면을 32개 가로띠로 나누고, 삼각형도 노드끼리 나눠 맡는 방식
- 처음엔 모든 노드가 전체를 훑어서 **공통 작업이 94%** 를 먹었다
  → 32개를 써도 거의 안 빨라졌다. 기하 단계도 나누니 13.4배가 됐다
- **프레임 시간 = 가장 느린 노드** (전체÷개수가 아니다)

> **LLM 이식에도 같은 함정이 있다.** 나누는 방식을 처음부터 잘 정할 것.

## 핵심 수치 — 이게 이 프로젝트의 현실이다

한 문장 = 프롬프트 62토큰 + 출력 70토큰 = **132토큰**
토큰마다 가중치 10.1M 개를 한 번씩 곱한다 → **13.3억 MAC**

### 칩별 소요 시간 (계산값, 실측 아님)

| 칩 | 1개 | 32개 | 64개 | 주소공간 | 패키지 |
|---|---|---|---|---|---|
| Z80 | 57시간 | 1.8시간 | 54분 | 뱅크 필요 | DIP-40 |
| MOS 6502 | 44시간 | 1.4시간 | 42분 | 뱅크 필요 | DIP-40 |
| **MC68000P8** | 5.0시간 | **9.3분** | 4.7분 | OK | **DIP-64** |
| **MC68000P12** | 3.2시간 | **6.0분** | 3.0분 | OK | **DIP-64** |
| MC68020 | 25분 | 48초 | 24초 | OK | PGA-114 |
| MC68030 | 16분 | 30초 | 15초 | OK | PGA-128 |
| Intel 486DX2 | 6.4분 | 12초 | 6초 | OK | PGA-168 |

계산 근거: MAC 하나 = 곱셈 사이클 + 부대비용(로드·누산·분기).
68000 은 `mac_68k.s` 실측 108T, 나머지는 매뉴얼 사이클로 추정.

### 에뮬레이터 실측 (2026-09-09 확인)

`python emulate.py --quick` 를 돌린 결과 — **이게 가장 믿을 만한 수치다.**

```
클럭 8.0MHz · MAC 100사이클 · 노드 32개 · tree 토폴로지
  총 MAC       1,296,863,040
  최대 노드    39,258,240 MAC     ← 이 노드가 시간을 결정한다
  링 전송      16,422,116 바이트 · 홉 10
  계산         8.18분
  통신         25.7초 (5.0%)
  합계         8.61분
```

출력도 맞았다 (블록 4개, 기대 4개).

> **메모리에 적힌 "3.8분" 은 틀렸다.** 실측은 **8.61분** 이다.
> 다음 사람은 8.61분을 기준으로 쓸 것. 위 표의 9.3분은 손계산이고,
> 에뮬레이터 8.61분이 더 정확하다 (MAC 100T vs 108T 차이).

### 메모리

int8 가중치 10.1MB. 32개로 나누면 **노드당 0.31MB**.

- 68000: 주소공간 16MB → 뱅크 스위칭 불필요 (이게 68000 을 고른 이유)
- Z80·6502: 64KB뿐 → 뱅크 회로가 노드마다 필요

## 칩 독립적으로 만드는 방법 ← 이번 작업의 핵심

사용자가 원하는 건 **"칩을 바꿔 끼울 수 있는 구조"** 다.
칩마다 어셈블리를 새로 짜면 안 된다. 이렇게 나눈다:

```
┌─────────────────────────────────────────┐
│  공통 (칩 무관) — 한 번만 만든다          │
│   · 가중치를 노드별로 쪼개는 도구          │
│   · 노드 간 통신 규약 (메시지 형식)        │
│   · 호스트 쪽 조립·검증 코드              │
│   · 에뮬레이터 (사이클표만 바꿔 끼움)      │
├─────────────────────────────────────────┤
│  칩별 (이것만 새로 짠다) — 200줄 이하      │
│   · MAC 커널 (곱셈 누산 루프)             │
│   · 링 송수신 루틴                        │
│   · 사이클표 (MULS 몇 T, ADD 몇 T…)      │
└─────────────────────────────────────────┘
```

**칩을 바꿀 때 바꾸는 것은 MAC 커널 하나뿐**이 되게 설계할 것.
`mac_68k.s` 가 그 예다. 다른 칩이면 `mac_6502.s`, `mac_z80.s` 를 만들면 된다.

에뮬레이터도 `--chip 68000` / `--chip 6502` 처럼 사이클표만 갈아끼우게.

## 넘어야 할 기술 문제 3가지

### 1. 정수 연산의 정확도 — 아직 검증 안 됨

C++ 엔진은 활성값이 float32 인데(W8A32), 옛날 CPU 에는 FPU 가 없다.
`emulate.py` 가 이미 정수로 바꿔 놨다 (`quant_act`, `mac_int`).

**문제는 그게 정확한지 아직 안 재봤다는 것이다.**
에뮬레이터는 문장 하나만 확인했다 (블록 4개, 맞음).

- `verify.py` 의 200개를 정수 경로로 돌려서 몇 개 맞는지 확인할 것
- 떨어지면 양자화 폭을 조정 (`quant_act(bits=15)` 를 만져본다)
- LayerNorm 의 나눗셈·제곱근, Softmax 의 exp 가 특히 위험하다

**이게 1단계이자 가장 중요한 관문이다.** 여기서 정확도가 안 나오면
하드웨어를 만들어도 소용없다.

### 2. 나누는 방식

3D 렌더러에서 배운 것 — **공통 작업이 병목이 된다.**

LLM 은 층(layer)마다 전체 활성값이 필요하므로,
어떻게 나눠도 노드 간 통신이 생긴다. 후보:

| 방식 | 나누는 것 | 통신량 | 비고 |
|---|---|---|---|
| 층 분할 | 8층을 4노드씩 | 층당 활성값 320개 | 파이프라인 가능 |
| 행 분할 | 행렬 행을 32등분 | 매 층마다 전체 모음 | 통신 많음 |
| 헤드 분할 | 어텐션 헤드 8개 | 중간 | 8노드까지만 |

**층 분할이 유력하다** — 토큰을 파이프라인으로 흘리면
노드가 놀지 않는다. 다만 첫 토큰 지연이 생긴다.

먼저 에뮬레이터로 세 방식을 비교해서 정할 것.

### 3. 검증 방법

**하드웨어 사기 전에 에뮬레이터로 끝까지 검증한다.**

1. PC 에서 정수 전용 버전 만들기 → 200개 검증 통과
2. 노드 분할 시뮬레이션 → 결과가 단일 노드와 같은가
3. 사이클 계산 → 실제 몇 분인가
4. 그 다음에야 4노드 시제품 → 32노드

## 작업 순서 (권장)

```
0단계  emulate.py 를 읽고 지금 상태를 파악한다  ← 먼저 이것부터
       정수 연산·행 분할·통신량 계산이 이미 들어 있다

1단계  정확도 검증 (아직 안 됨)
       emulate.py 는 문장 하나만 확인했다. verify.py 의 200개를
       정수 경로로 돌려서 몇 개 맞는지 봐야 한다.
       ← 여기서 떨어지면 양자화 폭(Q8.8 등)을 조정

2단계  분할 방식 비교 (지금은 행 분할만)
       층 분할·헤드 분할을 넣어 통신량을 비교.
       지금 행 분할은 매 층마다 전체를 모아야 해서 통신이 5% 인데,
       층 분할이면 더 줄 수 있다 (대신 첫 토큰 지연)

3단계  칩 갈아끼우기 구조
       사이클표를 표로 빼서 --chip 68000/6502/z80 로 고르게.
       mac_68k.s 처럼 칩별 커널을 따로 두되 나머지는 공유

4단계  실제 시간 확정
       칩별 표를 근거 있는 수치로 채운다

5단계  (선택) 하드웨어
       4노드 시제품 → 32노드. 예산 74만원, DESIGN.md 참조
```

## 판단이 필요한 것 — 사용자에게 물어볼 것

**이 프로젝트의 목표가 무엇인가?**

- (A) **전시·시연** — LED 32개가 파도치며 계산하는 그림.
  9분이 걸려도 상관없다. → 68000 그대로, 하드웨어까지 간다
- (B) **실용** — 실제로 쓸 만한 속도.
  → 68020 이상 필요, 값이 6배(₩800,000) 오르고 PGA 라 조립이 어렵다
- (C) **시뮬레이션만** — 에뮬레이터로 "된다"만 보이고 하드웨어는 안 산다.
  → 4단계까지만. 비용 0

메모리 기록으로는 **(A) 전시용**이 목표였다. 다만 사용자가
"다른 칩도 써보고 싶다"고 했으므로 확인이 필요하다.
