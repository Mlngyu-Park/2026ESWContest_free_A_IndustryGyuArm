# RACHEL 을 시프트·곱셈·표만으로 — 68000 정수 이식 기록

**결론: 됐다.** 자작 언어모델 RACHEL(10.1M)의 추론 경로에서 실수 연산을
전부 걷어냈다. 남은 것은 정수 곱셈(`MULS`), 시프트(`ASL/ASR`), 룩업 표,
그리고 나눗셈(`DIVS`) 몇 번뿐이다 — 전부 MC68000 이 가진 명령이다.

| | 실수(C++ 원본) | 정수(dusk) |
|---|---|---|
| Spark 200문장 정확도 | 95.0% | **98.5%** (197/200) |
| 로컬 60문장 | 100% | **100%** |
| 틀린 문장 | 142·181·190 | **같은 3개** |
| 추론 경로 `double`/`pow`/`exp`/`sqrt`/`tanh` | 있음 | **0줄** |
| 68000 32노드 8MHz 한 문장 | (FPU 없이 약 77분) | **8.2분** |

정수판이 C++ 보다 3개 더 맞은 것은 우열이 아니다. 두 엔진은 60문장 중
57개가 똑같은 출력이고, 나머지는 근소한 logit 이 반올림 방향 차이로
갈린 것이다.

가중치는 `rachel_cpp/rachel_v9.bin`, 검증은 `nano_llm/val.jsonl` 앞 200문장.
2026-09-09 ~ 09-11, 사흘 걸렸다.

---

## 1. 왜 정수여야 하나

68000 에는 FPU(소수점 연산 장치)가 없다. 실수 덧셈 하나를 소프트웨어로
흉내내면 약 316 사이클 — 정수 덧셈(8T)의 39배다. 한 문장 13억 MAC 이면
정수 8.2분, 실수 77분이다.

**FPU 는 곱셈기가 아니다.** 68000 에 곱셈기는 있다(`MULS`, 16×16→32, 70T).
없는 것은 "이 값이 지금 몇 배인가"를 자동으로 관리해 주는 부분이다.
그래서 68881 코프로세서를 붙여도 빨라지지 않는다(float 곱셈 40~100T,
정수 MULS 와 비슷). 정수로 짜는 게 맞고, 현대 AI 가속기도 int8 로 추론한다.

정수 이식이 어려운 이유는 연산이 아니라 **스케일 관리**다. FPU 가 자동으로
하던 "몇 배인가"를 손으로 들고 다녀야 하고, 이번에 잡은 버그는 전부 거기서 났다.

## 2. 무엇을 무엇으로 바꿨나

| 실수 연산 | 정수 대체 | 68000 비용 | 정확도 |
|---|---|---|---|
| `pow(2, shift)` | 시프트 한 번 | ASL/ASR | **오차 0** (같은 연산이다) |
| `/ sqrt(hd)` | 상수 0.158 을 Q15(5178)로 곱함 | MULS 1회 | 0.003% |
| `exp()` (softmax) | 2의 거듭제곱 분해 + 16칸 표 + 선형보간 | 시프트 + MULS 1회 | 0.12% |
| `tanh()` (GELU) | 512칸 표(1KB) + 선형보간 | MOVE.W + MULS 1회 | 0.008% |
| `sqrt()` (LayerNorm) | 뉴턴법 정수 제곱근 | DIVS 몇 회 | 0.00009% |
| 배율 곱셈·나눗셈 | `Scale`(가수+시프트) 곱, 역수는 한 번만 | MULS + 시프트, DIVS 1회 | — |

표는 곱셈보다 싸다 — 표 읽기 `MOVE.W` 8T, 곱셈 `MULS` 70T. GELU 를 조각별
직선으로 근사했을 때 오차 0.169 였던 것이 표로 바꾸니 0.00004 가 됐다.
**더 정확하면서 더 빠르다.**

## 3. 핵심 설계 — 스케일을 어떻게 다루나

### Scale = 가수 / 2^시프트

```c
typedef struct { int32_t mant; int shift; } Scale;   /* 실제값 = mant / 2^shift */
```

곱셈은 가수끼리 곱하고 시프트는 더한다. 값에 적용하는 것은
`MULS` 한 번 + 시프트 한 번이다. 가수는 [2^28, 2^30) 로 정규화해 둔다
(16비트로 두면 상대오차 0.0015% 가 8층에 쌓여 층당 5% 가 된다).

도구: `mk_scale(num, den)` · `mul_scale(a, b)` · `sc_div(a, b)` ·
`sc_mul(v, s)` · `sc_mul_safe(v, s)`. 전부 int64 연산만 쓰고, 실수 계산과
대조해 오차 0.005% 이하를 확인했다.

### 스케일을 층 사이로 들고 다니지 않는다

처음에는 지수(exp)를 층 사이로 넘기는 방식을 썼다. 오차가 쌓여 20% 에서
막혔다. 검증된 방식은 단순하다:

```
연산마다   ① 입력 최대값으로 스케일을 만든다
           ② int16 으로 눌러 정수 곱셈
           ③ 결과에 스케일을 곱해 바로 되돌린다
```

LayerNorm 은 평균을 빼고 표준편차로 나누므로 스케일을 지운다 — 층마다
기준이 초기화되어 오차가 누적되지 않는다.

### 활성값 규약

- 행렬곱 입력: int16 (±32767), 결과: int32 누산 → **int64** 로 (아래 버그 1)
- 잔차: int32, 두 항의 스케일을 작은 쪽 시프트에 맞춰 더함
- KV 캐시: int16 (±32000) + 위치마다 배율·스케일 저장
- 어텐션 점수: **int32** Q11 (1.0 = 2048), 클램프 없음 (아래 버그 8)
- softmax 출력: Q15 확률 (합 32767)
- LayerNorm 출력: 1σ = 4096

## 4. 잡은 버그 — 전부 실측 근거가 있다

순서대로. 하나 잡을 때마다 정확도가 계단처럼 올랐다.

| # | 버그 | 증상 | 해결 |
|---|---|---|---|
| 1 | **int32 누산 넘침** — q·k 40개 합 429억, 행렬곱 1280개 합 53억 > 21억 | 점수 +1.32 가 −0.37 (부호 뒤집힘) | int64 누산, 68000 은 `ADD.L`+`ADDX.L` |
| 2 | LayerNorm gamma 를 `>>7` 로 근사 | 1.0001 → 0.9141, 원소마다 오차 다름 | scale 을 정수로 곱하고 `>>` |
| 3 | 활성값 범위 ±1.0 부족 | LayerNorm 출력 1.68 이 1.0 에 포화 | ±4.0 규약, GELU 표도 ±4 로 |
| 4 | KV 캐시에 그 시점 스케일 미저장 | 긴 답의 37~93번째 글자만 틀림 | 위치별 `kmant/kshift/vmant/vshift` 저장 → 91%→100% |
| 5 | `scale_q` 가 q16 이라 작은 스케일 못 담음 | bias scale 0.00013 → 8.57 이 8 로 잘려 6.6% 오차, LN 출력 부호 뒤집힘 | q30 (`SC_BITS`), `65536` 이 흩어져 있어 상수로 통일 |
| 6 | `mk_scale` 안에서 `den*2^28` 이 int64 넘침 | q30 전환 후 배율이 0 | 한쪽만 옮기며 비교 |
| 7 | **LayerNorm 분산 누산 int64 넘침** — 13억² × 320 = 5.5e20 | sd 가 42억, 정규화 출력 150배 작아짐, L1 에서 값 1600배 폭발 | 편차를 24비트로 미리 줄여 제곱 |
| 8 | **`exp_q` 가 정확히 2배** — 2^(1-fp)/2^(ip+1) 트릭의 마지막 /2 누락 | exp(−0.743)=0.476 이어야 하는데 0.917, softmax 납작 | `m >> ip` + 표 선형보간 |
| 9 | **어텐션 점수 int16 클램프** (±16) | 뾰족한 헤드에서 7~9개 위치가 상한에 붙어 L4 오차 65% | int32 점수 + `dusk_softmax_q32` |
| 10 | softmax `e[256]` 고정 배열 | v9 는 ctx 448 — 256 뒤 위치를 버림 | 512 |
| 11 | 시프트 전에 자리 미확보 | 잔차 합이 4984(int32 의 0.0002%)로 떨어져 작은 값 소실 | `keep` 만큼 덜 밀고 분모 보정, 오차 71%→0.003% |

버그 1·6·7 은 전부 **오버플로**다. 값이 커질수록 int32/int64 경계를 넘는데,
넘치면 부호가 뒤집혀 조용히 틀린다. 정수 이식에서 제일 무서운 종류다.

## 5. 검증 방법 — 이게 핵심이었다

### 정답에서 한 단계씩

C++ float 원본에서 출발해 행렬곱 → LayerNorm → GELU → 어텐션 순으로
하나씩 정수로 바꾸며 200문장을 돌렸다. LayerNorm 을 바꾼 순간 0% 가
되어 범인이 바로 나왔다. 한꺼번에 바꿨으면 못 찾았다.

### 나란히 계산 → 대조 → 전환

정수판을 실수판 옆에서 계산하되 **결과는 실수판을 쓰고** 오차만 잰다.
오차가 충분히 작아지면 그때 전환한다. 3/3 기준선을 유지한 채 원인을
하나씩 가를 수 있었다.

### 층별 지문 대조

C++ 에 계측을 넣어 층마다 `x[0..3]` 을 찍고, dusk 와 나란히 비교했다.
코사인 유사도로 방향을, 벡터최대 기준 오차로 크기를 본다.

### 상대오차는 착시를 만든다

작은 원소에서 상대오차 71% 가 나왔는데, 그 원소는 벡터 최대의 0.017% 였다.
**벡터 최대 기준 오차**를 봐야 실제 영향을 안다 (그 기준 0.003%).

### 계측이 계산을 덮어쓰지 않게

`att[]` 가 이미 exp 를 거친 뒤에 "점수" 라고 찍어 부호가 뒤집힌 줄 알았다.
진단 코드도 검증 대상이다 — 사본을 떠서 대조할 것.

### 가중치 버전부터 확인하라

한때 "100% 에서 75% 로 떨어졌다" 고 오판했다. 실제로는 9/10 에 다단계
문장을 넣어 재학습한 `rachel_v9.bin` 이 문서에 기록되지 않은 채 있었고,
옛 v8 로 새 검증 데이터를 돌리고 있었다. C++ 원본도 같은 73% 였다.
정확도가 이상하면 **가중치 파일과 `val.jsonl` 의 시각부터 대조**할 것.

## 7. 한계 — 정직하게

- **6단계 명령 1/8 실패**는 모델(v9)이 못 배운 것이다. C++ float 도 똑같이
  틀린다. 정수화와 무관하다.
- **사이클 수치(100T/MAC, 8.2분)는 손계산**이다. `mac_68k.s` 의 명령별
  타이밍을 매뉴얼에서 더한 값이고, 실제 68000 칩으로 재본 적이 없다.
- `pkill -x dusk` 직후 3초 만에 재시작하면 옛 프로세스와 경쟁해 새것이
  죽을 수 있다. 4초 이상 기다리거나 `pgrep -x dusk` 가 비었는지 보고 띄울 것.
- 이 코드는 PC 에서 68000 을 **흉내내며 사이클을 세는 것**이다. 실제 68000
  어셈블리(`mac_68k.s`)로 옮기는 일은 남아 있다 — 다만 이제 옮길 대상이
  전부 정수 연산이라 옮길 수 있다.

## 8. 배운 것

정수 이식에서 어려운 것은 곱셈이 아니라 **스케일 관리**였다. 곱셈은 처음부터
오차 0 이었다. 열한 개 버그가 전부 "이 값이 지금 몇 배인가", "이 자리에
담기는가" 에서 났다.

그리고 **softmax 는 배율에 민감하다.** "차이만 쓰니 공통 배율을 생략해도
된다"는 틀렸다 — exp 는 비선형이다. 뺄 수 있는 것은 덧셈 상수뿐이다.

작업 일지(시행착오 전체)는 `SHIFT_worklog.md`, 정확도 진단은 `ACCURACY.md`.
