# 시프트만으로 — 68000 에서 실수 연산 없이 돌리기

**68000 에는 FPU 가 없다.** 소수점 계산을 소프트웨어로 흉내내면
한 문장에 77분이 걸린다(정수는 8.2분). 그래서 실수를 아예 안 쓰는
코드로 다시 짜야 한다.

이 문서는 **어떤 실수 연산을 어떤 정수 연산으로 바꿀 수 있는가**를
정리한 것이다. 결론부터: **전부 가능하다.**

---

## FPU 는 곱셈기가 아니다

먼저 오해를 정리한다. 68000 에 **곱셈기는 이미 있다** — `MULS` 가
16×16→32비트를 70사이클에 한다. 하드웨어 곱셈기다.
(Z80·6502 에는 이게 없어서 시프트+덧셈을 반복해야 한다.)

없는 것은 **소수점을 관리하는 부분**이다.

| 68000 이 가진 것 | 없는 것 (FPU 가 하던 일) |
|---|---|
| `MULS` 곱셈 70T | 지수 맞추기 (0.5 + 0.001 처럼 크기가 다른 수) |
| `DIVS` 나눗셈 158T | 정규화 (계산 후 소수점 자리 다시 잡기) |
| `ADD.L` 덧셈 8T | 반올림 규칙, 무한대·NaN 처리 |
| `ASL/ASR` 시프트 | |

float 덧셈 하나를 소프트웨어로 하면 약 316T 다 — 정수 덧셈(8T)의 **39배**.

**즉 FPU 를 붙여도 빨라지지 않는다.** 68881 코프로세서의 float 곱셈은
40~100 사이클로 정수 `MULS`(70T)와 비슷하다. FPU 는 정확도와 편의를
주지 속도를 주지 않는다.

## 대체표 — 전부 시프트·곱셈·표로 된다

| 실수 연산 | 왜 되나 | 정수 대체 | 정확도 |
|---|---|---|---|
| `pow(2, shift)` | 지수가 2의 거듭제곱이다 | 시프트 한 번 (`<<` / `>>`) | **완전히 같음** |
| `/ sqrt(hd)` | `hd=40` 고정 상수 | 0.158 을 Q15(5178)로 곱함 | 오차 0.003% |
| `exp()` (softmax) | 2의 거듭제곱 + 표 16칸 | 시프트 + 표 읽기 | **구현됨** (`exp_q`) |
| `tanh()` (GELU) | 512칸 표 + 선형보간 | 표 읽기 + 곱셈 1번 | **구현됨** (`GELU_TAB`) |
| `sqrt()` (LayerNorm) | 뉴턴법 | 정수 제곱근 | **구현됨** (`isqrt32`) |
| 나눗셈 `/` | 역수를 한 번 구해 곱함 | `DIVS` 1회 + `MULS` n회 | 68000 표준 기법 |

핵심은 **`pow(2, shift)` 가 시프트 그 자체**라는 것이다.
편하려고 `pow()` 를 썼을 뿐, 지수가 2의 거듭제곱이니 `<<` 한 번이면
끝나고 **결과가 완전히 같다**.

### 이미 만들어 둔 정수 커널

```
dusk_node.c   exp_q()      2의 거듭제곱 + POW2_FRAC 표 16칸
              isqrt32()    뉴턴법 정수 제곱근
gelu_tab.h    GELU_TAB[]   512칸 x 2바이트 = 1KB
```

GELU 를 조각별 직선으로 근사했더니 오차가 0.169(17%)였는데,
**표로 바꾸니 0.00004** 가 됐다. 68000 에서는 표 읽기가 `MOVE.W` 8T 고
곱셈이 `MULS` 70T 라 — **더 정확하면서 더 빠르다.**

## 스케일을 정수로 다루는 방법

FPU 가 자동으로 해주던 "이 값이 지금 몇 배인가" 를 손으로 관리해야 한다.
배율을 `(가수, 지수)` 쌍으로 들고 다닌다.

```c
typedef struct { int32_t mant; int shift; } Scale;
/* 실제값 = mant / 2^shift */
```

곱셈은 가수끼리 곱하고 지수는 더한다. 적용은 곱셈 한 번 + 시프트 한 번.

```c
static int64_t sc_mul(int64_t a, Scale s) {
    int64_t r = a * s.mant;
    if (s.shift > 0) {
        int sh = s.shift;
        r += (r >= 0 ? (1LL<<sh)/2 : -((1LL<<sh)/2));   /* 반올림 */
        r >>= sh;                                        /* 시프트 */
    }
    return r;
}
```

이 도구를 실수 계산과 대조해 검증했다:

```
sc_gt (크기 비교)  5가지 경우 전부 실수와 일치
sc_div (나눗셈)    오차 0.005% 이하
```

**도구 자체는 정확하다.**

## 정수화에서 실제로 물린 것들

원리는 단순한데 구현에서 함정이 많았다. 실측으로 잡은 것만 적는다.

### 1. int32 누산 넘침

```
q·k 내적 : 40개 × 32767²      = 429억  > int32(21억)
행렬곱   : 1280개 × 127 × 32767 = 53억  > int32
```

실제로 `-933,560,989`(부호가 뒤집힌 값)이 나왔고, 어텐션 점수가
`+1.32` 여야 할 자리에 `-0.37` 이 나왔다.

**해결**: 어텐션은 폭을 ±5000 으로 줄이고, 행렬곱은 int64 로 누산.
68000 에서 int64 누산은 `ADD.L` + `ADDX.L` 두 명령이라 부담이 없다.

### 2. 시프트로 상수를 근사하면 안 되는 곳

gamma 를 `>>7` 로 근사했더니 1.0001 이 0.9141 이 됐다(9% 오차).
게다가 **원소마다 오차가 달라서** 벡터 모양이 일그러졌다.

**해결**: `scale` 을 q16 정수로 곱하고 `>>16`.
`MULS` 70T 가 들지만, LayerNorm 은 층당 320개뿐이라 무시할 비용이다
(행렬곱은 층당 100만 번).

> **원칙**: 자주 도는 루프는 시프트, 가끔 도는 곳은 곱셈.
> 정확도가 필요한 곳에서 시프트로 아끼면 손해가 더 크다.

### 3. 나눗셈의 내림 편향

`>>` 와 정수 나눗셈은 항상 0 쪽으로 버린다. 수십만 번 누적되면
결과가 한쪽으로 쏠린다. 반올림을 넣으면 `ADD.L` 한 번이면 된다.

```c
r += (r >= 0 ? half : -half);   /* 반올림 */
r >>= sh;
```

### 4. 값을 좁은 자리에 담는 손실

잔차 값이 int32 의 **0.003%** 밖에 안 썼다 — 31비트 중 16비트만 쓰고
15비트를 버린 셈이다. 자리를 채우려 여러 방법을 시도했으나 스케일
계산과 얽혀 있어 전부 실패했다 (0% ~ 75%).

**이건 아직 안 풀렸다.**

완전 정수화가 정확도를 깎지 않았다는 뜻이다.

### 어텐션 정수화에서 잡은 버그 셋

**1. `exp_q` 가 정확히 2배였다**
2^-(ip+fp) = 2^(1-fp)/2^(ip+1) 트릭에서 마지막 /2 가 빠져
`(m<<1)>>ip` 로 계산했다. exp(-0.743) 이 0.476 이어야 하는데 0.917.
softmax 가 납작해져 확률비가 2.1 대신 1.1 로 나왔다. → `m >> ip`.
표 16칸 계단오차(칸당 4.4%)는 **선형보간**으로 0.12% 까지 줄였다 (MULS 1회).

**2. 점수를 int16(Q11, ±16)에 담아 클램프됐다**
뾰족한 헤드는 점수가 16 을 넘는다. L4 에서 헤드당 7~9개 위치가
32767 에 붙어 상위 순서가 뭉개졌고, 어텐션 출력 오차가 **65%** 까지 튀었다.
→ 점수를 int32 로 두고 클램프 없는 `dusk_softmax_q32` 를 만들었다.
정규화도 `>>15` 내림 대신 q20 역수 + 반올림 (위치 150개면 내림만으로
확률 질량 0.46% 가 샌다).

**3. `e[256]` 고정 배열** — v9 는 ctx 448. 256 뒤 위치를 통째로 버리고 있었다.

### 다시 확인한 원칙

- **softmax 는 배율에 민감하다.** "차이만 쓰니 공통 배율을 생략해도 된다"는
  틀렸다 — exp 는 비선형이다. 뺄 수 있는 건 덧셈 상수뿐. 진짜 배율을
  `Scale` 곱(`mk_scale`/`mul_scale`/`sc_div`)으로 전부 만들어야 한다.
- **계측이 계산을 덮어쓰면 진단이 거짓말을 한다.** `att[]` 가 이미 exp 를
  거친 뒤에 "점수" 라고 찍어 부호가 뒤집힌 줄 알았다. 사본(`fsc`)을 떠서 대조할 것.
- **나란히 계산 → 대조 → 전환.** 이번에도 이 순서라 원인을 하나씩 가를 수 있었다.

## 오늘 잡은 버그 — 전부 오버플로였다

### 1. LayerNorm 분산 누산이 int64 를 넘쳤다 ← 결정타

```
x 최대 13억 → d*d = 1.7e18 → 320개 합 = 5.5e20  >  int64(9.2e18)
```

그 결과 `sd` 가 42억(2^32 근처)이라는 엉뚱한 값이 되고,
정규화 출력이 **150배 작아졌다** (±1 이어야 하는데 ±0.0066).

이것 때문에 L0 은 맞는데 **L1 에서 값이 1600배로 폭발**했다.

**해결**: 편차를 미리 줄여서 제곱한다.
```c
while (dmx > 16777215 && vsh < 30) { dmx >>= 1; vsh++; }   /* 24비트로 */
int64_t d = (x[i] - mean) >> vsh;   vs += d*d;
...
int64_t dd = vsh ? (d >> vsh) : d;  /* nv 계산에서 맞춘다 */
```
68000 관점: 시프트 한 번 추가일 뿐이다.

### 2. 시프트 전에 자리를 확보해야 한다 (keep)

`>>30 >>sx` 를 그대로 하면 합이 4984 까지 떨어진다 (int32 의 0.0002%).
나중에 키워봐야 이미 잃은 뒤다.

```c
int keep = 0;
while (pk > 0 && keep < 30 && (pk << (keep+1)) < 2000000000LL) keep++;
int ta = 30 + sx - keep;                 /* 덜 민다 */
xs_.shift = cs - dn + keep + 29 - 30;    /* 분모도 그만큼 */
```
오차 71% → 0.003%.

### 3. 시프트는 합쳐서, 반올림은 한 번만

`>>30` 과 `>>sx` 를 따로 하면 반올림 기회를 두 번 잃는다.
`>>(30+sx)` 로 합친다.

### 4. attn 잔차와 MLP 잔차는 짝이다

한쪽만 정수화하면 스케일 규약이 어긋나 값이 폭발한다.

## 남은 것: 어텐션 점수

점수 = `acc x kexp[t2] x kmant[t2] / 2^kshift[t2] / sqrt(hd)`

**막힌 지점**: `acc x kx` 가 int64 를 넘어 `acc` 를 22칸 줄이는데,
그러면 `acc>>22 = 238` 로 정보가 다 날아간다.

```
acc ~ 1e9,  kx = kexp x kmant ~ 1.05e16
acc x kx = 1.05e25  >>  int64(9.2e18)
```

**다음에 시도할 것**: `acc` 대신 **`kx` 를 먼저 줄인다.**
`kexp` 와 `kmant` 는 둘 다 큰 값이라 미리 정규화할 여지가 있다.

그리고 **모든 위치가 같은 시프트**를 써야 한다 — softmax 는 위치
간 차이로 확률을 만들므로, 위치마다 다른 시프트를 쓰면 점수가
뒤죽박죽이 된다 (실측: 가장 작아야 할 값이 -2억으로 튀었다).

## 검증 결과 — 어디까지 확인됐나

### ✅ 확인된 것

**1. 정수 이식 자체는 성공했다.**

dusk(정수)와 C++ 원본(float)을 60문장으로 대조했다:

```
출력이 같은 문장: 59/60
C++ 정확도 : 44/60 = 73.3%
dusk 정확도: 43/60 = 71.7%
```

**C++ 원본도 73.3% 다.** 틀리는 문장(3,4,6,10,13)이 dusk 와 정확히
같다 — 모델 한계지 이식 문제가 아니다.

> 한때 "100% 에서 75% 로 떨어졌다" 고 판단했는데 **틀렸다.**
> 200문장 앞쪽과 20~60 구간의 난이도가 달랐던 것이다.
> 기준선은 항상 **C++ 원본과 대조**해서 잡아야 한다.

**2. q16 → q30 전환으로 층 오차가 126배 줄었다.**

```
q16:  L0 -1.410%  →  L7 -2.402%
q30:  L0 +0.000%  →  L7 +0.019%
```

logits 가 정답과 소수점 둘째 자리까지 일치한다:
```
정답 pos166: [1]36.33 [5]31.40
dusk pos166: [1]36.30 [5]31.40
```

**3. `Scale` 도구는 정확하다.**
```
sc_gt (크기 비교)  5가지 경우 전부 실수와 일치
sc_div (나눗셈)    오차 0.005% 이하
```

### ❌ 아직 안 된 것: 잔차의 완전 정수화

**정수 잔차 계산 자체는 정확하다.** 실수판과 나란히 돌려 대조했다:

```
벡터최대 기준 오차:  L0 0.00292%  L1 0.00165%  L2 0.00111%
```

그런데 **정수판 결과를 실제로 쓰면 L1 에서 값이 1600배로 폭발한다**:

```
정답      L0 -0.0341   L1 -0.2978
정수 전환 L0 -0.0339   L1 -47.9479   ← L0 은 맞고 L1 에서 터진다
```

L0 → L1 사이(`ra_ln` 또는 `ra_mv`)에서 스케일 규약이 어긋난다.
정수 잔차가 내놓는 shift(57)가 실수판(40)보다 훨씬 큰데,
다음 단계가 그 범위를 감당하지 못하는 것으로 보인다.

**부품은 전부 검증했다:**

| 검증 대상 | 결과 |
|---|---|
| `mk_scale` (큰 값 포함 6가지) | 오차 0.00000% |
| `quant_to` 왕복 | 오차 0.0001% |
| 정수 잔차 계산 | 벡터 기준 0.003% |
| `mul_scale` 연쇄 | shift 51, 안전 |
| `ra_ln` int64 누산 | 넘침 없음 |

**부품이 다 맞는데 합치면 틀린다** — 스케일 규약의 전파 문제다.

### 이번에 알아낸 것 (다음에 쓸 것)

**1. 상대오차만 보면 착시가 생긴다.**

작은 원소에서 상대오차 71% 가 나왔는데, 알고 보니 그 원소는 벡터
최대의 0.017% 였다. **벡터 최대 기준 오차**를 봐야 실제 영향을 안다.
그 기준으로는 0.003% 였다.

**2. 시프트는 합쳐서 한 번에, 반올림도 한 번만.**

`>>30` 하고 `>>sx` 를 따로 하면 반올림 기회를 두 번 잃는다.
`>>(30+sx)` 로 합치면 작은 값이 덜 뭉개진다.

**3. 시프트 전에 자리를 확보해야 한다 (keep).**

`>>30 >>sx` 를 그대로 하면 합이 4984 까지 떨어진다 (int32 의 0.0002%).
나중에 `dn<0` 으로 키워봐야 이미 잃은 뒤다. 미리 덜 밀어야 한다.

```c
int keep = 0;
while (pk > 0 && keep < 30 && (pk << (keep+1)) < 2000000000LL) keep++;
int ta = 30 + sx - keep;          /* 덜 민다 */
...
xs_.shift = cs - dn + keep + 29 - 30;   /* 분모도 그만큼 */
```

이걸로 int32 를 60% 채웠고 오차가 71% → 0.003% 가 됐다.

**4. 부호 규약 정리**

| 항목 | 의미 | 분모 보정 |
|---|---|---|
| `dn > 0` | 값을 줄였다 | `- dn` |
| `keep` | 덜 밀어 값이 크다 | `+ keep` |
| 가수 곱셈 | 값이 2^30 배 | `>>30` 으로 되돌림 |

**5. attn 잔차와 MLP 잔차는 짝이다.**

한쪽만 정수화하면 스케일 규약이 어긋나 값이 폭발한다.
반드시 같이 바꿔야 한다.

### 다음에 할 일

**L0 → L1 사이를 파야 한다.** 정수 잔차 결과(shift 57)를 받은 뒤
`ra_ln` 과 `ra_mv` 가 어떻게 처리하는지 값을 찍어 볼 것.

구체적으로:

1. 정수 잔차 직후 `xv`·`xs_` 를 찍고
2. `ra_ln` 직후, `ra_mv` 직후를 각각 찍어
3. 어느 단계에서 1600배가 되는지 특정한다

`ra_ln` 이 `*xsc = mk_scale(1, LN_UNIT)` 로 스케일을 **덮어쓴다**는
점이 의심스럽다 — 입력 스케일을 무시하므로 shift 57 이 들어와도
출력은 항상 같은 규약이 된다. 그 사이 값 크기는 13억인데
`nv = d * LN_UNIT / sd` 가 그걸 감당하는지 확인할 것.

**작업 규칙** (이번에 효과를 본 것):

- 정수판을 **나란히 계산해 대조만** 하고, 통과하면 전환한다
  (`DUSK_ICMP` 방식). 바로 전환하면 원인을 못 가린다.
- 한 번에 한 곳만 바꾸고 `./t3.sh` (20초) 로 확인한다
- 3/3 을 확인한 **직후** 백업을 뜬다

## 결론 — 시프트 변환은 가능한가

**원리적으로는 전부 가능하다.** 근거:

- `pow(2,shift)` 는 시프트 그 자체 — 오차 0
- `exp`/`tanh`/`sqrt` 는 표와 뉴턴법으로 이미 구현됨
- 계산의 90%(행렬곱)는 **이미 정수만 쓴다**
- q30 전환으로 정밀도가 충분함이 증명됨 (층 오차 0.019%)

**실제 구현은 미완이다.** 잔차 스케일 전파에서 막혀 있고,
추론 경로에 실수 연산이 27줄 남아 있다.

지금 상태로는 68000 에서 못 돈다 — 그 점은 분명히 해둔다.
