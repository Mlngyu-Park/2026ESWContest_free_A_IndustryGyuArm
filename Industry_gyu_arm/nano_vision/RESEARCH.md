# 카메라 비전 AI — 만들 수 있나 (조사)

**조사만 한 문서다. 아직 아무것도 만들지 않았다.**

목표를 이렇게 잡았다:

- **엄청나게 복잡한 장면**에서 사람·물체를 감지
- **CPU only, 60fps 이상**
- **모델 10MB 정도**
- RACHEL 처럼 **전부 직접** 만들기

결론부터: **된다. 단 두 가지를 받아들여야 한다.**
10MB 를 다 쓰지 말 것(6MB), 그리고 매 프레임 신경망을 돌리지 말 것.

숫자는 전부 이 노트북에서 직접 쟀다. 인터넷에서 가져온 값이 아니다.

## 2. 실측 ① — float32 로는 안 된다

클래스 20종, 입력 416x416, 8스레드, torch float32:

| 모델 폭 | 파라미터 | int8 크기 | 중앙값 | fps |
|---|---|---|---|---|
| w=24 | 1.57M | 1.6MB | 37.1ms | 27.0 |
| w=32 | 2.76M | 2.8MB | 48.4ms | 20.7 |
| w=48 | 6.13M | 6.1MB | 68.8ms | 14.5 |
| **w=64** | **10.83M** | **10.8MB** | **104.8ms** | **9.5** |

**10MB 모델이 9.5fps.** 목표의 6분의 1이다. 여기서 끝냈으면 "안 된다" 였다.

---

## 3. 실측 ② — 진짜 병목은 파라미터가 아니라 해상도

같은 모델(w=48)에 입력 크기만 바꿨다:

| 입력 | 중앙값 | fps | 256 대비 |
|---|---|---|---|
| 256x256 | 34.0ms | 29.5 | 1.0배 |
| 320x320 | 41.4ms | 24.2 | 1.2배 |
| 416x416 | 61.0ms | 16.4 | 1.8배 |
| 512x512 | 106.1ms | 9.4 | 3.1배 |
| 640x640 | 162.5ms | 6.2 | **4.8배** |

파라미터를 10.8M → 6.1M 로 **43% 줄여** 번 것이 1.5배인데,
해상도를 640 → 256 으로 내리면 **4.8배**다.

> **모델을 줄이는 것보다 해상도를 내리는 게 훨씬 크게 듣는다.**
> 대개 반대로 알고 있다.

그런데 여기가 함정이다 — **복잡한 장면은 높은 해상도를 원한다.**
멀리 있는 작은 물체는 256 에서 그냥 사라진다. 이게 이번 목표의 정면충돌 지점이다.

---

## 4. 실측 ③ — int8 이 판을 뒤집었다

fbgemm(AVX512-VNNI) 로 int8 양자화:

| 모델 / 입력 | float32 | int8 | 배수 |
|---|---|---|---|
| 6.1MB / 416 | 51.7ms (19fps) | **16.3ms (61.4fps)** | **3.18배** |
| 10.8MB / 416 | 64.3ms (16fps) | 24.2ms (41.4fps) | 2.66배 |
| 6.1MB / 320 | 26.2ms (38fps) | 12.8ms (78.0fps) | 2.05배 |
| 2.8MB / 416 | 22.8ms (44fps) | 12.5ms (79.9fps) | 1.83배 |

**여기서 "된다" 로 바뀌었다.**

### ⚠ RACHEL 과 정반대인 점 (중요)

RACHEL 6-1 에서 int8 전면 양자화가 "겨겨겨겨" 로 실패해 **W8A32**
(가중치만 int8) 로 후퇴했다. **비전에서는 그러면 안 된다.**

- RACHEL 이 실패한 이유: 320차원이라 활성값 분포가 좁아 뭉개짐
- 비전 CNN 은 활성값 분포가 넓고 채널별 스케일을 따로 줄 수 있다
- 무엇보다 **W8A8 이어야 VNNI 하드웨어 가속을 받는다.** W8A32 면 위 3배가 없다

RACHEL 경험을 그대로 가져오면 **틀리는** 유일한 지점이라 굵게 적어둔다.

---

## 5. 실측 ④ — 신경망 밖에서 13ms 가 샌다 ★ 가장 중요

이 조사에서 제일 값진 발견이다. 1280x720 웹캠 → 416 입력 기준:

| 단계 | 중앙값 |
|---|---|
| 리사이즈 416x416 | 1.22ms |
| 색변환+전치+정규화 (**float32**) | **4.49ms** |
| 〃 (**uint8 유지**, int8 모델용) | **0.20ms** |
| 격자 디코딩 + 임계값 | 0.79ms |
| **NMS 후보 300개** | 2.22ms |
| **NMS 후보 1000개** | **6.52ms** |
| **NMS 후보 3000개** | **17.61ms** |

**신경망 제외 합계 약 13ms.** 60fps 예산 16.67ms 중
**신경망에 3.6ms 밖에 안 남는다.**

즉 신경망만 16.3ms(61fps) 여도 **실제 파이프라인은 30fps 도 안 나온다.**
RACHEL 8장의 "좋은 것만 골라 봤다" 와 똑같은 함정이 여기 있다.

두 가지가 눈에 띈다:

1. **float32 4.49ms → uint8 0.20ms (22배).** int8 로 가야 할 이유가
   속도 3배만이 아니다. 전처리까지 22배 싸진다.
2. **NMS 가 복잡한 장면에서 신경망보다 비싸진다.** 후보 3000개면 17.6ms.
   복잡한 장면이 목표이므로 이건 반드시 C++ 로 옮겨야 한다.

---

## 6. 실측 ⑤ — 답: 매 프레임 돌리지 않는다

RACHEL 10장의 "**덜 하는 것**" 을 그대로 적용했다.
60fps 로 들어와도 물체는 그렇게 빨리 안 움직인다.
신경망은 가끔 돌리고 사이는 **추적(계산)** 으로 메운다.

추적 비용 실측:

| | 시간 |
|---|---|
| 칼만 예측 30개 상자 | **0.034ms** |
| 칼만 예측 60개 상자 | 0.057ms |
| IoU 매칭 30x30 | 0.050ms |

**신경망의 500분의 1이다.** 사실상 공짜다.

검출 프레임 25.0ms (전처리 1.4 + 신경망 16.3 + 후처리 7.3), 추적 0.05ms 로 계산하면:

| 신경망 주기 | 평균 프레임 | 실효 fps | |
|---|---|---|---|
| 매 프레임 | 25.00ms | 40.0 | △ |
| **2프레임에 1번** | **12.53ms** | **79.8** | ✅ |
| 3프레임에 1번 | 8.37ms | 119.5 | ✅ |
| 4프레임에 1번 | 6.29ms | 159.0 | ✅ |

**2프레임에 한 번이면 79.8fps.** 목표를 넘긴다.
파이썬 후처리 기준이고, C++ 로 옮기면 더 좋아진다.

## 7. 그래서 권하는 설계

| 항목 | 값 | 왜 |
|---|---|---|
| 파라미터 | **약 6M (int8 6MB)** | 10MB 다 쓰면 41fps. 6MB 가 61fps |
| 입력 | **416x416** | 320 은 작은 물체를 놓치고, 512 는 못 따라감 |
| 양자화 | **W8A8 (전면 int8)** | VNNI 가속. RACHEL 의 W8A32 아님 |
| 스레드 | **4~8** | 로봇 제어와 나눠 쓸 것 |
| 신경망 주기 | **2프레임에 1번** + 칼만 추적 | 40fps → 79.8fps |
| 후처리 | **C++ NMS** | 복잡한 장면에서 파이썬 NMS 가 신경망보다 비쌈 |
| 예상 | **약 80fps, 6MB** | |

10MB 예산 중 **6MB 만 쓰고 4MB 를 남긴다.** 남은 4MB 는
정확도가 부족할 때 폭을 늘리는 데 쓰거나, 특징 벡터 모델에 준다.

---

## 8. 스레드 — RACHEL 과 또 반대

RACHEL 6-3 에서 OpenMP 를 빼서 4배 빨라졌다. 비전은 반대다:

| 스레드 | 중앙값 | fps |
|---|---|---|
| 1 | 263.5ms | 3.8 |
| 2 | 158.2ms | 6.3 |
| 4 | 97.5ms | 10.3 |
| 8 | 63.6ms | 15.7 |
| 16 | 54.4ms | 18.4 |

**1 → 8 스레드에 4.1배.** RACHEL 은 320차원이라 스레드 만드는 비용이 더
컸지만, 비전은 합성곱 한 층이 RACHEL 전체 모델보다 크다.

다만 8 → 16 은 1.17배뿐이다(물리 8코어). **8을 넘길 이유가 없고,**
로봇 제어와 CPU 를 나눠 쓸 것을 생각하면 **4~8이 적당하다.**

## 9. "특정 사물 인식" 을 어떻게 할 것인가

여기가 RACHEL 3장이 그대로 재현되는 곳이다.

두 갈래가 있다:

| | 학습 때 정한 목록 | 보여준 물건 찾기 |
|---|---|---|
| 새 물건 추가 | **다시 학습** | **사진만 다시 찍음** |
| 모델이 하는 일 | 분류까지 | 특징 벡터만 |

**두 번째를 권한다.** "이 물건이 무엇인가" 를 신경망 가중치에 외우게
하지 말고, 신경망은 **특징 벡터 뽑기만** 시키고 **비교는 계산**으로 넘긴다.

```
사진 3장 등록 → 특징 벡터 저장 (계산)
카메라 → 검출(신경망) → 특징 벡터(신경망) → 저장분과 비교(계산) → 이름
```

RACHEL 에서 사전 찾기를 `hints.py` 33줄로 뺐더니 62.7% → 99.6% 였던 것과
**정확히 같은 구조**다. 벡터 비교는 계산이 완벽하게 하는 일이다.

> 원칙 재확인: 신경망에게 뭘 시키고 뭘 계산에 넘기느냐가 성능을 결정한다.

## 10. 정직하게 — 아직 모르는 것

이 조사는 **속도만** 쟀다. 무작위 가중치로 쟀으므로
**정확도는 하나도 모른다.** 아래는 아직 답이 없다:

- **6M 파라미터로 복잡한 장면의 정확도가 나오는가** — 속도는 됐지만 이게 진짜 문제다
- **학습 데이터를 어떻게 구하나** — RACHEL 은 규칙으로 합성했지만 이미지는 그게 안 된다.
  이 프로젝트에서 **가장 큰 미해결 문제**다
- 겹친 물체(가림)를 6M 이 견디는지
- int8 양자화 후 정확도 손실 (보통 1% 미만이지만 실제로 재봐야 함)
- 카메라 캡처 비용 (WSL2 에 카메라가 없어 못 쟀다. 3~5ms 예상)
- C++ 엔진 작성량 — RACHEL 은 307줄이었지만 CNN 은 합성곱·NMS·SIMD 까지라 더 크다

**속도는 "된다" 가 확인됐고, 정확도와 데이터는 확인되지 않았다.**

## 11. 나중에 시작한다면 순서

1. **데이터부터 정한다.** 여기서 막히면 나머지가 의미 없다
2. 파이썬 + torch 로 6M 모델 학습 (Spark 사용)
3. `test_real.py` 같은 **실사용 회귀시험** 먼저 만들기 — RACHEL 4장의 교훈
4. int8 양자화 (**W8A8**), 정확도 손실 확인
5. C++ 엔진 (합성곱 + NMS), 다중 스레드는 **넣는다**
6. 칼만 추적 붙여 2프레임 주기로
7. 전체 파이프라인 평균으로 측정 — **최솟값 보지 말 것**

## 12. 한 줄 요약

**10MB 를 다 쓰면 41fps, 6MB 로 줄이고 2프레임에 한 번만 돌리면 80fps.**

RACHEL 과 같은 결론이다 — 더 하는 게 아니라 **덜 해서** 풀렸다.
다만 int8 방식(W8A8)과 스레드(넣는다)는 RACHEL 과 **반대**다.
