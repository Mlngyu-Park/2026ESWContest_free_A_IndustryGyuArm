# 카메라 인식 — 영상으로 판·카메라·로봇·도킹을 읽어 디지털 트윈에 배치

**박민규 · 2026-10-07 기준 · 코드: `Industry_gyu_arm/cam_grid/`**

카메라로 작업대를 찍으면 아래 네 가지를 읽어 ARM STUDIO 공장 배치에 자동으로 반영한다.
- 목심 판(3×3 타일)
- 카메라 위치
- 로봇팔 위치·방향
- 도킹 스테이션 위치·색

숫자는 전부 녹화 영상 `shots/KakaoTalk_20261006_123735928.mp4`(1280×720, 94프레임, 3.9초)로 잰 값이다.

## 1. 한눈에 보기

```
영상 프레임
  │
  ├─ ① 구멍 찾기          큰 목심 구멍만 (작은 배수 구멍 제외)
  ├─ ② 격자 맞추기        구멍 → 판 격자 (호모그래피)
  ├─ ③ 프레임 추적        카메라 이동을 먼저 예상 → 칸 번호를 이어 붙임
  ├─ ④ 판 30×30 정하기    가장 많이 본 30×30 창 + 체크무늬 위상 → 원점 확정
  ├─ ⑤ 카메라 자세        격자에서 초점거리 추정 → 판 기준 카메라 위치·방향
  ├─ ⑥ 물건 찾기          '가려진 구멍' → 로봇 · 도킹(색)
  ├─ ⑦ 로봇 자세          받침 판의 목심 구멍 줄 → 위치 + 방향
  │
  ├──▶ ARM STUDIO 3D 뷰어: 카메라 · 1인칭 · 자동 배치
  └──▶ RViz: 판 · 카메라 · 로봇 · 도킹 마커 · 1인칭 패널
```

**AI(신경망)는 쓰지 않는다.** 모든 단계가 기하 계산과 규칙이다. 판의 크기와 무늬를 미리 알고 있으니, 그 사실로 맞추고 그 사실로 검산한다.

## 2. 바탕 사실 — 바뀌지 않는 것

| 항목 | 값 |
|---|---|
| 목심 간격 | 20 mm |
| 타일 | 200 mm = 10×10 칸 |
| 판 | 3×3 타일 = 30×30 칸 = 900 목심 |
| 타일 색 | 파랑·흰색 체크무늬 (영상 속 판: 모서리 넷과 가운데 흰색, 상하좌우 파랑) |
| 구멍 | 큰 구멍(목심)과 작은 구멍(배수)이 섞여 있다. 큰 구멍만 쓴다 |

모든 검산이 이 사실에서 나온다. 예를 들어 이어 붙인 판이 30칸을 넘으면 어딘가 잘못 붙인 것이다.

## 3. 단계별 작동

### ① 구멍 찾기 — `grid.detect_holes`

1. 판 영역 = 파랑(H 95~130, S>80) 또는 흰색(S<45, V>140)
2. 어두운 점 = `흐린 영상 − 영상` (구멍은 주변보다 어둡다), 문턱값 10
3. **크기로 큰 구멍만 고른다.** 크기 기준은 고정하지 않는다. 카메라 거리마다 구멍 크기가 달라지기 때문이다
   - 첫 프레임: 면적 분포를 **오츠 방식으로 두 무리**로 나눠 큰 무리를 쓴다 (작은 구멍 15~60, 큰 구멍 150~700 px²)
   - 이후 프레임: 앞 프레임에서 잰 격자 간격으로 정한다. **큰 구멍 면적 = 0.107 × (격자 간격 px)²** (실측 445개 중앙값)

### ② 격자 맞추기 — `grid.fit_full`, `grid.grow`

1. 이웃 구멍 사이 벡터에서 격자의 두 방향(기저벡터)을 찾는다
2. 구멍 하나를 원점 후보로 두고 기저벡터로 첫 격자를 만든다
3. **`grow`**: 예측한 격자점에 실제 구멍이 있으면(0.3칸 안) 짝으로 넣고 호모그래피를 다시 푼다. 6번 반복
4. 원점 후보 여러 개 중 가장 많은 구멍이 맞는 격자를 고른다

호모그래피는 4점으로 정해지고, **예측한 자리에 실제 구멍이 있는지가 곧 검산**이다.

| 결과 (사진 한 장) | 값 |
|---|---|
| 큰 구멍 | 447 (오츠 방식 474) |
| 한 격자에 맞음 | **419 (94%)** / 445 |
| 재투영 오차 중앙값 | 1.3 px |

### ③ 프레임 추적 — `grid.Board.add`, `grid.frame_motion`

**문제:** 앞 프레임 격자를 그대로 씨앗으로 쓰면, 카메라가 반 칸 넘게 움직일 때 **매 프레임 정확히 한 칸씩 미끄러졌다.** 구멍이 전부 똑같이 생겨서 옆 칸 구멍과 구별이 안 된다.

**해결:** **카메라 이동을 먼저 예상한다.**
1. ORB 특징점(3,000개)으로 두 프레임 사이 화면 이동(호모그래피)을 구한다. 로봇·도킹·판 가장자리처럼 하나뿐인 모양이 이동을 잡아 준다
2. `예상 격자 = 화면 이동 × 앞 프레임 격자`
3. 예상 격자를 실제 구멍에 맞춰 다듬는다(`grow`)

| 시험 (사진 한 장을 움직인 가짜 영상) | 칸 번호 어긋난 프레임 |
|---|---|
| 40프레임 (천천히) | 0 |
| 15프레임 (빠르게) | 0 |
| 10프레임 (아주 빠르게) | 0 |
| 가운데 8프레임 건너뜀 | 0 |
| 실제 영상 94프레임 | 0 |

### ④ 판 30×30 정하기 — `Board.window`, `Board.tile_phase`

**판 창:** 여러 프레임에서 본 구멍을 모으면 판 밖의 가짜도 섞인다 (로봇 몸통의 구멍, 흰 상자, 벽). 처음에는 판이 40×50칸으로 부풀었다. **"구멍은 반드시 판 안에 있고 판은 30×30"** 이므로, 가장 많이 본 30×30 창을 판으로 정한다.

| | 구멍 수 | 프레임에서 본 횟수 (중앙값) |
|---|---|---|
| 창 안 | 734 / 900 | **29번** |
| 창 밖 (버림) | 98 | **2번** |

**타일 위상:** 칸 색을 모아 체크무늬가 가장 잘 맞는 10칸 주기 위상을 찾는다 (일치율 82~88%). 흰 퍼즐 이음새를 흰 칸으로 잘못 읽는 것이 오차의 원인이다.

**원점 확정:** 구멍 수로 찾은 판 창 원점 (−12, −26) 과 체크무늬 위상 (8, 4) 이 **정확히 맞물렸다.** 서로 다른 두 방법이 같은 판 테두리를 가리킨다.

### ⑤ 카메라 자세 — `pose.py`

렌즈 값(초점거리)을 몰라도 된다 (휴대폰 영상). 격자는 **직각이고 가로·세로 간격이 같다**는 두 조건이 호모그래피에서 초점거리를 정해 준다 (화면 가운데를 주점으로 가정). 프레임마다 구해 중앙값을 쓴다.

| 결과 | 값 |
|---|---|
| 초점거리 | 1,174 px (94프레임 중 25~75% 가 1,156~1,199, **±2%**) |
| 직각 검산 | 0~0.011 (거의 0) |
| 카메라 높이 | 350 → 580 mm (영상 속 움직임과 일치) |
| 내려다보는 각 θ | 32° → 60° |
| 프레임 간 이동 | 중앙값 7 mm |
| 판 900개를 다시 투영한 오차 | 중앙값 2.7 px (1280×720) |

판 좌표계: 원점 = 판 첫 목심, x = i 방향, y = j 방향, z = 판 위, 단위 m.

### ⑥ 물건 찾기 — `objects.Tracker`

**원리: 가려진 구멍.** 판 900개 목심의 화면 위치는 프레임마다 안다. 화면 안에 있는데 안 보이는 구멍을 센다. 카메라가 움직이며 여러 방향에서 보니, 한 방향에서만 가려진 구멍은 다른 방향에서 보인다. **계속 안 보이는 구멍 = 물건 자리.**

실측하며 배운 규칙:

| # | 규칙 | 이유 (실측) |
|---|---|---|
| 1 | **타일 경계 줄(타일 안 0·9번째)은 판단에서 빼고 이웃으로 채운다** | 퍼즐 이음새에 걸려 구멍이 **한 번도** 안 잡힌다 (보임 점수 0) |
| 2 | **기준은 "주변 6칸 안 같은 종류 자리의 상위 25%"** | 먼 곳·파란 타일은 원래 덜 잡힌다. 판 전체 평균을 쓰면 먼 곳이 전부 '가려짐' |
| 3 | 가려진 칸의 색을 모아 **같은 색끼리** 묶는다 | 색 없이 묶으면 로봇·도킹·탐지 약한 곳이 하나로 붙는다 |
| 4 | **판 색은 물건 색으로 안 센다** (파란 타일 위 파랑, 흰 타일 위 흰색) | 안 빼면 파란 타일이 통째로 '파란 도킹' |
| 5 | **색 증거가 거의 없는 칸은 버린다** | 원래 잘 안 보이는 곳은 판 색 기록뿐 |
| 6 | 빨강 = H 158~ (보라 = S>90 일 때만) | 그늘진 빨강이 보라로 읽혀 가짜 보라 도킹 |
| 7 | **연속 3번 판정에 같은 색이 3칸 안에 있어야 인정** | 깜빡임 막기 |
| 8 | **'비었음'은 구멍이 실제로 4번 이상 보였을 때만** | 보임 점수가 1에서 시작해서, 덜 본 자리를 비었다고 착각 → 도킹 삭제 |

| 결과 | |
|---|---|
| 찾은 것 | 로봇 1 + 파랑·빨강·노랑 도킹 (실물과 같음) |
| 안정성 | 35번 프레임부터 끝까지 세 도킹 유지, 영상 2회 반복 재생에도 배치 변화 없음 |

### ⑦ 로봇 자세 — `camsync.robot_template`, `camsync.robot_pose_from_plate`

**로봇 받침 판에도 목심 구멍이 있고, 받침이 목심에 꽂히니 그 구멍도 판 격자 위에 있다.** 이걸 쓴다.

1. **받침 판 높이로 영상을 편다.** 받침 판도 비스듬히 찍혀 기울어 보인다. 카메라 자세로 프레임마다 **받침 판 윗면 높이(판 위 15 mm)** 에 맞춰 반듯하게 펴고 중앙값을 낸다. 받침 판 구멍은 또렷해지고 판 구멍은 번진다
2. 받침 근처 어두운 점 중 **판 격자에 3.5 mm 안으로 딱 맞는 것만** 받침 구멍으로 친다. 몸통 위 잡음은 격자에 안 맞아 걸러진다
3. 가장 많이 늘어선 한 줄 = 받침 앞 가장자리 구멍 줄 (이 영상: x 529·550·569·589 mm, y 370 mm, **4개**)
4. **앞뒤 축 = 구멍 줄에 수직**(판 격자 방향). **앞쪽 = 몸통 반대편**. 이걸 메쉬의 "기둥 → 앞 구멍 쌍" 방향과 맞춘다
5. 위치: 메쉬의 앞 구멍 쌍 가운데를 영상 구멍 줄 가운데에 맞춘다

결과: **방향 0°**, 받침 구멍 4개. (몸통만으로 잰 각은 334°, 26° 틀림 → 축은 구멍 줄로 정해야 한다)

**로봇 위치 버그 (고침):** 카메라가 읽는 것은 **받침 바닥 가운데**인데, 앱의 로봇 위치(`BASE_OFF`)는 **로봇 기준점(원점)** 이다. 받침 바닥 가운데는 기준점에서 **(241, −258) mm** 떨어져 있다. 그래서 `기준점 = 읽은 자리 − 회전 × 받침가운데로컬` 로 거꾸로 계산한다.

**실패한 방법 (기록):**

| 방법 | 실패 이유 |
|---|---|
| 가려진 영역의 길쭉한 방향 | 로봇이 키가 커서 몸통이 뒤쪽 구멍까지 가린다. 받침 111×87 mm 인데 가려진 영역 160×160 mm, 방향은 카메라를 따라감 |
| 받침 밑 목심 모양 맞추기 | 받침 밑 목심이 4×4 정사각형 → 네 방향 점수 같음 |
| 받침 3D 를 카메라 시점으로 투영 | 1·2등 차이 6% |
| 윤곽 엣지 맞추기 | 판 구멍 엣지가 빽빽해서 어디든 비슷 |
| 판과 다른 색 덩어리 | 몸통 번짐에 끌려감 |

## 4. ARM STUDIO 앱 연동

### 코드

| 파일 | 역할 |
|---|---|
| `cam_grid/camsync.py` | `analyse()` 영상 분석 전체, `CamSync`(`SYNC`) 재생·좌표 변환·상태 |
| `arm_studio_web.py` | `_camsync_*`, `h_cam_*`, `_cam_apply_once` (자동 반영), 뷰어 `/state` 의 `camsync`, `/camframe/<k>`, 뷰어 JS `camSync` |
| `arm_studio_pro.py` | `cam_load` · `cam_ctl` · `cam_status` · `cam_fit_plates`, 중계 경로 `/camframe` |
| `pro_ui/index.html`, `app.js` | ③ 연동 탭 **📷 카메라 동기화** |

### 좌표 맞추기

판의 첫 목심을 **앱 바닥판 왼쪽 아래 타일의 첫 목심**(타일 안 10 mm)에 맞춘다.

### 자동 반영 규칙

**손 배치 기능의 코드는 고치지 않는다.** 그 기능이 쓰는 함수(`set_robot_pose`, `env_clone`, `set_name`, `move_env`, `env_delete`, `add_plate`)를 부르기만 한다.

| 대상 | 규칙 |
|---|---|
| 로봇 | 받침 구멍으로 위치+방향을 찾았으면 **영상 하나에 한 번** 배치. 못 찾았으면 위치만, **원래 자리가 또렷이 비었을 때만** 옮김 (팔 밑이 받침처럼 보여 30 cm 튄 적 있음) |
| 도킹 추가 | 같은 색 앱 도킹이 있으면 데려오고, 없으면 복제해서 만든다 |
| 도킹 이동 | 5 cm 넘게 벗어날 때만 |
| 도킹 짝짓기 | 같은 색이면 16 cm 안, 색이 달라도 6 cm 안이면 같은 도킹. 색은 다수결 |
| 도킹 삭제 | 그 자리가 **또렷이 비었음이 두 번 연속**일 때만 |
| 반영 주기 | 0.5초마다, 재생 시각까지 카메라가 본 만큼 |

### 화면 (③ 연동 → 📷 카메라 동기화)

| 버튼 | 동작 |
|---|---|
| 불러오기 | 영상 분석 (10~20초). 경로는 `cam_grid` 기준 또는 절대 경로 |
| 재생 / 정지 | |
| 1인칭 켜기/끄기 | 3D 뷰어를 카메라 눈 시점으로 (영상 비율 그대로, 위아래 검은 띠) |
| 1인칭 보기 바꾸기 | **영상+트윈 → 트윈만 → 영상만**. 트윈만일 때 **휠로 확대·축소** (0.25~6배, 시야각만 바뀜) |
| 자동 반영 켜기/끄기 | 끄면 바닥 고리 표시만 |
| 바닥판 맞추기 | 영상에서 읽은 판 크기(3×3)대로 앱 바닥판을 더한다 (빼지는 않음) |
| 판 90° 회전 · 판 옮기기 | 판 정렬을 손으로 고칠 때 (◀▶▲▼ 한 칸, 타일 단위) |

3D 뷰어 표시: 주황 = 카메라·보는 범위, 하늘색 = 판 가운데→카메라 선, 빨강 = 판 테두리, 바닥 고리 = 읽은 물건 (자홍 = 로봇, 그 색 = 도킹).

|---|---|
| 초록 점 / 빨강 선 / 노랑 선 | 판 900 목심 / 테두리 / 타일 경계 |
| 하늘색 선 · 주황 공 · 사각뿔 | 판 가운데→카메라 (θ, φ), 카메라 위치, 보는 범위 |
| 자홍 원기둥 / 색 원기둥 | 로봇 / 도킹 |
| camera view (1st person) 패널 | 카메라 눈으로 본 장면을 실제 영상 위에 겹침 |

기준 좌표계는 `board`(판)이다. 영상 메시지는 `array.array('B', …)` 로 넣어야 빠르다 (프레임당 4.7 ms).

## 6. 실행 도구

| 명령 | 하는 일 |
|---|---|
| `python live.py` | 실시간 카메라 미리보기. **x(ㅌ)** 캡처, **ㅂ(q)** 격자 판정, Esc 끝. `conda activate gyu_arm` 후 실행 (`conda run` 은 키 입력이 안 됨) |
| `python cam.py snap` | 한 장 찍어 격자 맞추기 |
| `python cam.py rec 15` | 15초 녹화 |
| `python cam.py track 영상.mp4` | 판 이어 붙이기 + 판 그림 |
| `python cam.py show 영상.mp4` | 영상 위에 판 목심(초록 점)을 덧그려 재생·저장 |
| `./cam_rviz.sh 영상.mp4` | RViz |

**카메라 연결 (WSL):** 윈도우 PowerShell(관리자)에서 `usbipd attach --wsl --busid 1-2 --auto-attach`. **창을 닫으면 끊긴다.** Logi C270 은 MJPG 1280×720.
**C270 프레임이 떨어지면:** 어두울 때 카메라가 스스로 fps 를 낮춘다 → `v4l2-ctl -d /dev/video0 -c exposure_dynamic_framerate=0`.

## 7. 한계와 남은 것

| 항목 | 상태 |
|---|---|
| 실시간 카메라 | **녹화 영상만** 된다. 판 위치를 영상 전체에서 찾고 재생하는 방식 |
| 도킹 뽑기·옮기기 | 로직은 있으나 **그런 장면이 담긴 영상으로 시험하지 못했다** |
| 로봇 방향 | 받침 구멍이 **한 줄로 2개 이상** 보여야 함. 못 찾으면 위치만 |
| 메쉬에 없는 판 | 실물 받침 앞에 세로 틈 있는 흰 판이 있는데 `base_link` 메쉬에는 없다 (확인 필요) |
| 노란 도킹 | 덩어리가 작게 잡혀 다른 도킹보다 덜 정확 |
| 흰 받침 + 흰 타일 | 받침이 흰 타일 위에 있으면 색 구분이 약해진다 (이 영상은 파란 타일 위) |
| 판 정렬 | 앱 바닥판 왼쪽 아래 타일에 맞춤. 앱 바닥판이 실물과 다르면 [바닥판 맞추기] 필요 |
| 시험 방식 | 앱을 켜면 시작 코드가 `calib.json` 을 다시 쓰므로, 반영 로직은 **가짜 앱**(`tests/fake_apply.py`)으로, 화면은 **뷰어만 띄운 시험 서버**(`tests/viewer_test_server.py`) + playwright 로 확인했다 |

### 9-2. 카메라

### 9-3. 찍는 방법

| 항목 | 권장 |
|---|---|
| 판 | 3×3 타일 전체가 영상 어딘가에 한 번씩은 담기게 (네 귀퉁이 포함) |
| 움직임 | 판 위를 천천히 한 바퀴. 여러 방향에서 볼수록 '가려진 구멍' 판정이 정확해진다 |
| 로봇 받침 | 받침 판의 목심 구멍이 **한 줄로 2개 이상** 보이는 각도가 있어야 방향을 정한다 |
| 길이 | 4초(94프레임)로 됨. 길수록 정확하지만 메모리가 늘어난다 (아래) |
| 조명 | 판의 파랑·흰색이 구별될 만큼. 강한 반사광은 흰 칸으로 잘못 읽힌다 |

### 9-4. 계산 자원 (AMD Ryzen 7 8845HS 8코어 16스레드 · 메모리 15GB · WSL2)

| 작업 | 시간 | 메모리 |
|---|---|---|
| 격자 추적만 | **84 ms/프레임** (1280×720), 64 ms (960×540), 51 ms (640×360) | — |
| 앱 [불러오기] 분석 전체 (격자 + 물건 + 로봇 자세) | **22초 / 94프레임** (약 0.23초/프레임) | **최대 3.0 GB** |
| RViz 노드 | 4.7 ms/프레임 | — |
| 1인칭 배경 영상 (JPEG 960 폭) | 프레임당 약 68 KB | 영상 길이에 비례 |

**메모리 주의:** 분석이 영상 프레임 전체를 메모리에 올리고, 판·받침 판 높이로 편 그림을 프레임 수만큼 쌓아 중앙값을 낸다. **4초에 3 GB** 이므로, 긴 영상(예: 30초)은 그대로 넣으면 메모리가 부족할 수 있다. 실시간으로 바꿀 때는 프레임을 쌓지 않고 누적하는 방식으로 고쳐야 한다.

### 9-5. 판·작업대 조건

| 조건 | 이유 |
|---|---|
| 판은 **20 mm 목심, 10×10 타일, 파랑·흰 체크무늬** | 격자 맞추기·검산·원점 확정이 전부 이 사실에 기댄다 |
| 판은 평평하게 | 판 전체를 한 평면(호모그래피)으로 본다 |
| 도킹은 **판 색(파랑·흰)과 다른 색** | 파란 도킹은 파란 타일 위에서는 색 판정을 건너뛰고 흰 타일 쪽에서 정한다 |
| 로봇 받침은 목심에 꽂힌 상태 | 받침 구멍이 판 격자 위에 있어야 방향을 정한다 |
