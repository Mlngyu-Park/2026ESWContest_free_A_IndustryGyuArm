## 2. 설계 원칙 — AI 경계선

> **AI 는 말을 블록으로 바꾸는 일까지만 한다. 좌표·경로·충돌·모터는 전부 계산이 한다.**

AI 는 두 곳에만 있다. 소리를 글자로 바꾸는 곳과, 글자를 블록으로 바꾸는 곳이다. 그 사이와 그 뒤는 전부 결정론적 계산이라, 같은 블록은 언제나 같은 관절각을 낸다.

이유는 안전이다. 로봇은 틀리면 물건이 깨지고 사람이 다친다. "대체로 맞는" 답을 내는 부품을 좌표를 만드는 자리에 두지 않는다. AI 가 만들 수 있는 것은 블록 목록뿐이고, 블록이 관절각으로 바뀌는 경로에는 AI 가 없다.

이 원칙의 효과는 실측으로 확인했다. 같은 크기의 모델에서 "빨간 도킹이 몇 번인가" 같은 표 조회를 신경망에 시켰을 때는 색 지칭 정확도가 **65.2%** 였다. 이 조회를 20여 줄짜리 계산(`hints.py`)으로 옮기자 **99.6%** 가 됐다. 두 값 모두 같은 검증셋 267문장으로 쟀다.

## 3. 하드웨어

### 3-1. 기준 로봇

| 항목 | 값 |
|---|---|
| 기체 | SO-ARM101 — STS3215 서보 6개, **5축 팔 + 그리퍼** |
| 서보 | Feetech STS3215 × 6 (ID 1~6) |
| 통신 | 시리얼 1 Mbps, 데이지체인 |
| 연결 | USB 시리얼 (`/dev/serial/by-id/...` 자동 인식). WSL 에서는 usbip 로 넘겨받는다 |
| 그리퍼 | j6 |

Dynamixel(XC/XM430, Protocol 2.0) 로봇도 같은 화면으로 다룬다. UR15 는 시뮬레이션 전용으로 등록돼 있다.

### 3-2. 관절 축 — 모든 제어 규칙의 출발점

```
j1  Z축 회전   팔 전체를 좌우로 돌린다. 기울기와 무관
j2  X축 회전   ┐
j3  X축 회전   ├ 세 축이 평행 → 세 각의 합이 곧 그리퍼 기울기
j4  X축 회전   ┘
j5  Y축 회전   돌리면 무조건 기운다 → 항상 0 으로 고정
j6  그리퍼     열기·닫기 전용
```

### 3-3. 모터 파라미터 (실측 튜닝값)

| 상수 | 값 | 의미 |
|---|---|---|
| `BAUD` | 1,000,000 | 시리얼 속도 |
| `GAIN_KP/KD/KI` | 64 / 64 / 4 | 위치 PID. 공장값 32/32/0 은 이 팔에 약했다 |
| `SAFE_VEL` | 150 | 이동 속도 상한 |
| `SAFE_ACCEL` | 8 | 가속. 높이면 덜덜 떨린다 |
| `TORQUE_LIMIT` | 250 | 토크 상한 |
| `DEADZONE` | 10 카운트 | 모터 데드존 (실측) |
| `END_TOL` | 6 raw | 도착 판정 ≈ 0.53° ≈ 엔드이펙터 3 mm |

게인 튜닝 전후: 정지 오차 18 raw(1.58°) → **4 raw(0.35°)**, 진동 0. 중력 때문에 남는 오차를 적분항(Ki)이 지운다. Ki 를 0 으로 두면 팔이 목표 아래에서 멈춘 채 버틴다.

### 3-4. 안전장치

- **관절 한계를 모터 EEPROM 에 기록한다.** 소프트웨어가 죽어도 모터가 스스로 범위를 벗어나지 않는다.
- **정지 = 즉시 토크 해제.** 감속이 아니라 힘을 끊는다.
- **로봇 불일치 차단.** 3D 에서 UR15(8축)를 고른 채 실물 전송을 시도하면 `real_robot_ok()` 가 막는다.
- **말로 실물을 움직이려면 두 번 확인한다.** "실물 실행"이라고 하면 "실물 실행 확인"이라고 다시 말해야 움직인다.

## 4. 좌표계와 툴 중심

### 4-1. cr_7 (툴 중심)

로봇이 "어디에 있는가"를 말할 때의 기준점이다. j6 링크에서 `[-9, 39.5, 39.3] mm` 떨어진 곳으로, SolidWorks 에서 그리퍼 회전 원의 중심에 잡은 좌표계다. URDF 에서 계산하며 하드코딩이 아니다.

`axis_7` 은 움직이는 죠(jaw)에 붙어 있어서, 그리퍼를 열면 위치가 바뀐다. 그래서 툴 중심을 잴 때는 j6 를 기준각(`J6_TOOL_REF`)으로 고정하고 계산한다. 그리퍼가 열려 있든 닫혀 있든 같은 좌표가 나온다.

### 4-2. 잡는 높이 — 계산하지 않고 고정

```
115 mm   도킹 스테이션 높이
+ 10 mm  도킹 윗면 → 그리퍼가 닿는 면      (GRASP_FACE_DZ)
+ 37 mm  잡는 면 → cr_7 중심               (GRASP_DZ_DEFAULT, 실측 36.67)
────────
= 162 mm 바닥 기준 잡는 점
```

메쉬로 매번 계산하면 오차가 쌓이고 도킹 종류마다 값이 흔들린다. 한 번 실측해 고정하는 편이 정확하고 재현된다. 접근·상승 여유는 60 mm(`GRASP_LIFT`)다.

### 4-3. 목심 격자

바닥판은 20 mm 간격의 목심(구멍) 격자다. 타일 하나가 200 mm(10×10칸)이고, 판은 3×3 타일(30×30칸)이다. 설비는 이 격자에 맞춰 놓인다.

## 5. 기구학 — 계산 영역의 핵심

### 5-1. 순기구학 (FK)

URDF 를 읽어 관절 체인을 만들고, 관절마다 변환 행렬을 곱해 끝점 위치를 얻는다. 로봇이 바뀌면 URDF 만 바꾸면 된다. `fk(q)` 는 j6 원점을, `tool_pos(q)` 는 툴 중심(cr_7)을 준다.

### 5-2. 수평 구속 — 「물컵 규칙」

j2·j3·j4 가 평행하므로 **j2+j3+j4 = 0** 을 지키면 그리퍼가 항상 수평이다. 물이 든 컵을 들고 옮겨도 쏟아지지 않는 자세다. 이 시스템의 IK 는 기본적으로 이 구속을 건다.

- 미세조정 보정도 같은 구속을 지킨다. j3 에 +5° 를 주면 j4 가 자동으로 −5° 를 받는다 (`level_offset`).
- 수평 오차는 실측 최대 **1.07°** 다 (허용 4°).

### 5-3. 역기구학 (IK)

| 함수 | 쓰임 |
|---|---|
| `ik_level` | 수평 유지 IK. 초기값을 여러 개 시도한다 (나쁜 초기값이면 도달 가능한 점도 실패로 나오기 때문) |
| `ik_tool` | 툴 중심 기준 IK. 수렴 기준 **0.002 mm** (커밋 b42c049) |
| `ik_general` | 수평 구속이 없는 로봇용 |
| `ik_tool_fast` | 해석적 IK 뼈대. 실측에서 틀린 값을 내 쓰지 않는다 |

### 5-4. 간편 이동 — 뽑기 → 수평 → 하강

이동 블록 하나는 세 구간으로 움직인다.

1. **뽑기**: 지금 자리에서 수직으로 올라간다
2. **수평**: 높이를 유지한 채 직교 격자 경로(`grid_path`, A*)로 옮겨 간다. "높이 유지 → 이동량 최소" 순으로 고른다. 도달 불가 영역은 항상 피한다
3. **하강**: 목표 위에서 수직으로 내려간다

`plan_simple` 이 이것을 계산한다. 경로 계산은 0.8~4.8초가 걸리고, 캐시가 있으면 0.8초다.

### 5-5. 도달표 — 미리 계산해 두는 것

- **목심 도달표** (658칸): 목심마다 도달 가능한 높이 구간을 **1 mm 단위**로 미리 계산해 둔다.
- **조종표** (143,667칸, 10 mm 격자): 조그 이동용. 시작할 때 0.7초에 불러온다.

핵심은 **로봇 기준 상대좌표로 저장**한다는 점이다. 로봇이나 설비를 옮겨도 표를 다시 계산할 필요가 없다 (재계산 0초).

### 5-6. 충돌검사

trimesh 로 메쉬를 다루고 fcl 로 검사한다. 로봇 링크(l2~l6)와 설비 STL 이 경로 위에서 겹치는지 실행 전에 확인한다 (`check_collision`).

**주의: 회피는 하지 않는다.** `plan_simple` 은 겹치는 구간을 찾으면 ⚠ 경고만 붙이고 그대로 진행한다 (docstring 에 명시). 충돌은 "검출해서 보여 주는 것"이지 "피해 가는 것"이 아니다.

## 6. 모션 실행 — 진동과의 싸움

### 6-1. 결론: 단순한 쪽이 이겼다

이동은 **"보내고 → 기다리고"를 반복**하는 것이 전부다. 도착 확인도, 오차 재측정도, 재보정도 하지 않는다.

### 6-2. 무엇을 뺐고 왜 뺐나

- **settle(도착 확인 + 과보정)을 뺐다.** 목표에 도달했는지 확인하고 오차만큼 다시 밀어 넣던 코드가 진동의 근원이었다. 밀면 넘어가고, 넘어가면 다시 되밀어 덜덜 떨었다.
- **이동 중 모터 읽기를 뺐다.** 걸음마다 `ROBOT.read()` 를 하면 250 ms씩 멈췄다.

예전 구형 앱(`arm_studio.py`)은 3개월 동안 진동이 없었는데, 이 방식이었다. 지금 코드는 그 방식으로 되돌린 것이다 (`SETTLE_ON=[False]`).

### 6-3. 그리퍼 — 여기만 폐루프

그리퍼는 물체를 쥐면 목표 각도에 못 가서, 도착 판정 대신 닫힘을 확인한다. 닫힘 완료까지 실측 3.2초가 걸린다.

### 6-4. 보정값의 분리

```
3D 화면    ← 이론 자세 (URDF 가 말하는 정답)
실물 모터  ← 이론 자세 + 보정값 (조립 오차·링크 휨을 메운 값)
```

보정값은 **자세마다, 로봇마다** 따로 저장한다 (`offsets: {'sts': [...], 'dxl': [...]}`). 시뮬레이션은 보정값을 쓰지 않는다. 3D 에는 조립 오차가 없으므로, 보정을 적용하면 화면이 오히려 틀린 자리로 간다.

## 7. 블록 파이프라인

### 7-1. 블록 7종

| 블록 | 기호 | 실제 동작 | 좌표 |
|---|---|---|---|
| 이동 | `@goto:<id>` | 뽑기 → 수평 → 하강 | **있음** |
| 잡기 | `@grasp:<물체>` | 열기 → 하강 → 닫기 → 상승 | 없음 |
| 놓기 | `@release:<도킹>` | 하강 → 열기 → 상승 → 닫기 | 없음 |
| 그리퍼 열기 / 닫기 | `@open` `@close` | 제자리 | 없음 |
| 하강 / 상승 | `@down` `@up` | 지금 XY 유지, 수직 | 없음 |

### 7-2. 좌표는 이동 블록만 갖는다

잡기와 놓기는 좌표가 없다. 지금 서 있는 자리에서 수직으로만 움직이고, 높이만 대상에서 얻는다.

예전에는 잡기가 스스로 대상의 XY 를 계산했다. 그러면 이동이 계산한 XY 와 잡기가 계산한 XY, **두 개**가 생긴다. 실측으로 23 mm 가 어긋났다. 좌표를 갖는 블록을 하나로 정해 두면 이 문제가 원천적으로 사라진다.

그래서 잡기·놓기 앞에는 그 대상으로 가는 이동 블록이 반드시 있어야 한다. 없으면 `seq_fix_moves()` 가 자동으로 넣는다.

### 7-3. 이동 블록은 실행하는 순간에 다시 계산한다

미리 계산한 경로를 쓰면, 파이프라인 중간에 물체가 옮겨졌을 때 옛 위치로 가 버린다. 그래서 이동 블록은 실행하는 순간 대상의 현재 위치로 경로를 다시 푼다.

단, 사용자가 미세조정해 **등록해 둔 자세**가 있으면 그것을 먼저 쓴다 (`_goto_pose_q`). 보정한 각도가 정답이기 때문이다. 이것은 실물에서만이고, 시뮬레이션은 계산 좌표로 간다.

### 7-4. 블록 어휘의 한계

블록은 "등록된 도킹 사이의 이송"만 표현한다. "파란 도킹 옆에", "펜 위에", "두 개 다", 밀기·누르기는 표현하지 못한다. 기구학 쪽에는 끝점 직선 이동(`plan_ee_line`)이 있지만, 블록과 말로는 노출돼 있지 않다. 힘 제어는 없다 (위치 제어만).

## 8. AI 층 — 말이 블록이 되는 과정

### 8-1. 음성 인식

| 엔진 | 위치 | 특징 |
|---|---|---|
| Spark Whisper (large-v3-turbo) | DGX Spark (18090 터널) | 정확하다. 네트워크가 필요하다 |
| Moonshine 한국어 27MB | 노트북 단독 | 네트워크 없이 돈다. 대신 정확도가 낮다 |

설정은 `auto` / `spark` / `moonshine` / `both` 가 있다. `both` 는 디버깅용으로, 두 결과를 로그에 나란히 찍는다.

Moonshine 은 입력 길이 한계(토큰 194개, 약 4.7초)가 있어서, 4초 창을 3초 간격으로 겹쳐 돌리고 겹친 부분을 이어 붙인다. 같은 말이 되풀이되는 루프와 끝에 붙는 헛말("감사합니다" 등)은 규칙으로 잘라낸다.

### 8-2. FIXER — 받아쓴 말 다듬기 (자작 7.5MB)

Moonshine 결과에만 적용한다. 실제 사례는 이렇다.

```
정답 : ...보라색 도킹 스테이션에 있는 초록색 펜을...
27MB : ...보라색 도킹 스테이션에 있는 [카페 스테이션에 있는] 초록색 펜을...
```

이 오염된 문장을 그대로 넣으면 블록이 10개(같은 이동 3번 반복)가 나오고, FIXER 를 거치면 7개(정상)가 나온다.

| 항목 | 값 |
|---|---|
| 구조 | 글자 단위 GPT, d320 L6 H8 ctx320 |
| 파라미터 | 7,603,200 (체크포인트 실측) |
| 크기 | int8 7.5MB |
| 속도 | 첫 호출 2.1초, 이후 25~31 ms (PyTorch) |

**안전장치.** 고친 결과에서 색이나 동작이 사라지거나, 색의 순서가 바뀌거나, 없던 색·동작이 생기거나, 반복이 생기면 **원문을 그대로** 쓴다. 틀린 교정은 안 고치는 것보다 나쁘기 때문이다.

음성 인식과 FIXER 를 합쳐 **WHISPER DUSK** 라고 부른다 (`whisper_dusk/`). OpenAI Whisper 와는 관계없는 이름이다.

### 8-3. 명령 해석 엔진 — 무엇이 실제로 도는가

앱 기본값은 `engine='auto'` 다 (줄 8270). 켜질 때 쓸 수 있는 LLM 을 이 순서로 찾는다 (`_llm_autodetect`, 줄 8279~).

1. **Spark 터널(18000)이 살아 있으면** → Spark 의 **Gemma 4 E4B 원본** (`gemma-4-E4B_q4_0-it.gguf`, 5.15 GB)
2. 없으면 노트북 ollama(11434) → 현재 깔린 것은 `gpt-oss:20b`
3. 둘 다 없으면 → **규칙 파서** (AI 없음)

화면에서 엔진을 RACHEL 로 고르면 그때 RACHEL 이 돈다. 선택지는 `auto` / `gemma` / `rachel`(C++) / `rachel_py` / `rule` 이다.

**Gemma 는 파인튜닝판이 아니다.** 원본에 긴 설명서(프롬프트)를 매번 붙여 보낸다. 설명서에는 지금 물체·도킹 목록과 각자의 색, 호칭 규칙, 블록 형식, "잡기 전엔 반드시 이동" 같은 규칙이 들어 있다. Gemma 4 는 "생각하기"를 끄지 않으면 블록을 못 만든다. 켜면 14초가 걸리고 블록 0개, 끄면 4.3초에 블록 8개였다 (`enable_thinking: false`).

8월 29일에 파인튜닝을 했지만, 그것은 **Gemma 3n** E4B 용 LoRA 이고 GGUF 로 합친 적이 없어 배포된 적이 없다. `SYSTEM.md` 의 "Gemma 4 E4B 파인튜닝"은 틀린 기록이다.

### 8-4. 힌트 — AI 에게 시키지 않는 일

`hints.py` 는 문장에서 색·번호 언급을 찾아, 언급 순서대로 도킹 id 를 나열해 입력에 붙인다.

```
장면: 보라=d2 빨강=d10 주황=d11 | 펜=초록@d2
힌트 d2 d10
보라색 도킹의 초록 펜 빨간 데로 옮겨
>
```

색 바로 뒤 5글자 안에 "펜·부품·물체·펜대"가 있으면 물건 색으로, 아니면 도킹 색으로 본다. 모델에 남는 일은 "어느 것이 출발·경유·도착인가"라는 말의 구조 판단뿐이다.

한계가 있다. 물건을 부르는 말이 이 4개 밖이면("빨간 거") 도킹 색으로 잘못 읽는다.

### 8-5. 출력 검증 계층

- `_flat_blocks`: LLM 이 블록 배열을 이중으로 포장해도 편다
- `_llm_expand`: 짧은 별명(`d11`, `#11`, `11`)을 실제 도킹 id 로 바꾼다
- `_resolve_item`: 등록되지 않은 대상을 가리키는 블록은 **버린다**
- JSON 껍데기가 깨지면 정규식으로 블록만 건져낸다

**검증의 범위.** 이 검증은 id 가 실제로 있는지만 본다. 같은 도킹으로 세 번 가는 블록처럼 **뜻이 틀린 순서는 걸러지지 않는다.** 그래서 이 시스템이 보장하는 것은 이렇다. 잘못된 목적지로 갈 수는 있지만, 등록되지 않은 대상이나 도달 불가능한 자세를 실행하지는 않고, 충돌은 실행 전에 표시된다.

### 8-6. 폴백 사슬

```
RACHEL / Gemma → 실패 → 규칙 파서 → 실패 → "무슨 뜻인지 모르겠습니다"
```

규칙 파서(`h_say` 의 규칙 분기, 줄 8674~)는 같은 검증 200문장에서 **30.0%** (60/200)를 맞힌다. 1단계 이송은 37%, 2단계 이상은 0% 다. "파란 도킹에 있는 펜을 노란 데 꽂아"에서 먼저 나온 도킹을 목적지로 착각하는 식으로 틀린다. 출발과 도착을 가르는 일은 규칙으로 안 되고 모델로 된다.

## 11. 미세조정(보정)과 저장

### 11-1. 흐름

```
블록 우클릭 [🎯 자세 등록 (미세조정용)]
   → ③연동 탭 [로봇을 이 자세로]
   → J1~J5 +/− 로 실물을 맞춘다
   → [보정 저장]
```

- **+/−** (`h_ft_step`): 보정값을 메모리에서 바꾸고, 고른 관절 하나만 실물로 보낸다. **파일에는 저장하지 않는다**
- **[보정 저장]** (`h_ft_save`): 보정값을 자세 각도에 녹여 넣고 보정값은 0 으로 만든 뒤, `calib.json` 에 바로 쓴다. 값을 하나로 만드는 구형 방식이다. 보정값을 따로 들고 다니면 같은 자리에 값이 둘이 되어 팔이 4.5° 씩 튀었다
- **[보정 초기화]**: 그 자세의 보정을 0 으로
- **영점(base) 다시 저장**: 그 로봇의 보정값을 **전부 0** 으로 초기화한다

### 11-2. 저장 파일

- `urdf/sts3215/Industry_gyu_arm_20260728_base/calib.json` — 로봇(URDF 패키지)마다 하나. 로봇을 바꾸면 경로도 같이 바뀐다
- 자세·보정, 파이프라인 블록, 설비 위치, 이름·색, 프리셋, 로봇 자리가 전부 여기 들어 있다
- 저장 직전에 **하루 한 번 자동 백업**한다 (`calib.json.YYYYMMDD.bak`). 자동으로 되돌리는 기능은 없다
- 자동 저장(`_macro_save`)은 "파일에는 있는데 메모리에는 없는 항목"을 지우지 않고 살려 둔다. 8월 24일에 설비·이름·자세가 통째로 날아간 사고 뒤에 넣은 장치다

## 13. 카메라 자동 배치 (개발 중)

카메라로 실제 판을 찍어, 도킹과 로봇이 몇 번 목심에 꽂혀 있는지 읽고 트윈에 자동으로 배치하는 기능이다. 코드는 `cam_grid/` 에 있다.

### 13-1. 원리

- 구멍 4개만 알면 호모그래피가 정해지고, 나머지 896개 위치가 계산으로 나온다
- 예측한 자리에 실제 구멍이 있는지로 **스스로 검산**한다
- 구멍은 다 똑같이 생겨서 한 칸 밀려도 검산을 통과한다. 이건 파랑·흰 체크무늬(10칸 주기)로 잡는다

### 13-2. 지금까지 된 것

| 단계 | 결과 |
|---|---|
| 사진 한 장 | 큰 구멍 447개 중 **419개(94%)** 가 한 격자에 맞음 |
| 카메라 자세 복원 | 거리 0.44 m · 기울기 24.4° · 방향 165.1° |
| 구멍 크기 | 고정값 대신 자동 — 첫 프레임은 면적 분포를 두 무리로 나누고, 이후는 면적 = 0.107 × (격자 간격 px)² |
| 영상 추적 | 격자만 보고 따라가면 **매 프레임 정확히 한 칸씩 미끄러졌다**. ORB 특징점으로 카메라 이동을 먼저 예상한 뒤 격자를 맞추게 바꿨다 |
| 가짜 영상 시험 | 40·15·10프레임, 중간 8프레임 건너뜀 → **모두 칸 번호 어긋남 0**. 30칸 검산 통과 |
| 타일 경계 | 체크무늬로 10칸 위상을 찾음, 일치율 87.7% (흰 퍼즐 이음새를 흰 칸으로 오판) |

### 13-3. 남은 것

- 실제 카메라 영상으로 시험 (카메라를 usbip 로 WSL 에 넘겨야 한다. WSL 커널에 `uvcvideo` 드라이버는 있다)
- 판 끝을 보고 원점 확정
- 도킹·로봇이 꽂힌 목심 번호 읽기 → 공장 배치에 자동 반영

한계가 하나 있다. 타일 하나 안의 10×10칸은 같은 색이라, 추적이 완전히 끊기고 타일 경계도 안 보이면 몇 칸 밀렸는지 되찾을 수 없다.

## 15. 장점

1. **안전한 구조.** AI 가 좌표를 만들지 않는다. 블록이 관절각이 되는 경로가 전부 계산이라, 같은 블록은 언제나 같은 동작을 낸다.
2. **작은 모델로 된다.** 10.1 MB 짜리 모델이 같은 과제에서 5.15 GB Gemma 원본보다 정확했다 (197 대 78, 200문장). 실행 메모리는 약 180분의 1이다.
3. **네트워크 없이 돈다.** RACHEL, Moonshine, FIXER 모두 노트북 CPU 에서 단독으로 돈다. 대회장 와이파이가 끊겨도 말로 조작할 수 있다.
4. **사람이 읽고 고칠 수 있다.** AI 의 출력이 블록이라 실행 전에 보고, 끌어서 고치고, 지울 수 있다. 스크래치처럼 초보자도 이해한다.
5. **화면과 실물이 같은 파이프라인.** 3D 에서 본 그대로 실물이 움직인다. 보정값만 실물 쪽에 더해진다.
6. **로봇을 바꾸기 쉽다.** URDF 만 바꾸면 기구학이 따라온다. STS3215, Dynamixel, UR15(시뮬)가 같은 화면에서 돈다.
7. **진동 없는 실물 동작.** 게인 튜닝과 settle 제거로 정지 오차 0.35°, 진동 0.
8. **미리 계산해 둔 표.** 도달표·조종표 덕분에 조회는 즉시, 재배치해도 재계산 0초.
9. **실패해도 멈추지 않는다.** LLM → 규칙 파서 → "모르겠습니다"로 이어지는 폴백 사슬이 있고, 등록되지 않은 대상은 실행 전에 버린다.
10. **모든 판단에 실측 근거가 있다.** 잡는 높이 37 mm, 게인 64/64/4, 가속 8, 구멍 면적 비율 0.107 같은 값이 전부 재서 정한 값이다.

## 16. 단점과 알려진 문제

### 16-1. 동작과 안전

| 문제 | 내용 | 위치 |
|---|---|---|
| **충돌을 피하지 않는다** | 검출해서 ⚠ 표시만 하고 그대로 진행한다 | `plan_simple` docstring |
| 뜻이 틀린 블록은 통과한다 | 검증은 id 가 있는지만 본다. 같은 도킹으로 세 번 가는 블록도 실행된다 | `_resolve_item` |
| 힘 제어 없음 | 위치 제어만. 물체를 세게 누르는지 알 수 없다 | |
| 블록 어휘가 좁다 | 등록된 도킹 사이 이송만. "옆에", "두 개", 밀기·누르기 불가 | §7-4 |

### 16-2. 보정과 저장

| 문제 | 내용 | 위치 |
|---|---|---|
| **같은 자리를 다시 등록하면 옛 자세로 간다** | 재등록하면 새 자세가 목록 맨 뒤에 추가되는데(`_2` 또는 좌표만 다른 이름), 실행은 이름 앞부분이 맞는 **첫 번째(옛)** 자세를 쓴다. 보정은 새 자세에 저장되므로 "저장했는데 이전 값으로 간다"가 된다 | 등록 줄 5118, 조회 줄 7533 |
| **+/− 만으로는 저장되지 않는다** | 메모리에만 바뀐다. 다른 자동 저장이 우연히 일어나면 남기도 해서, 남을 때와 날아갈 때가 섞여 보인다 | `h_ft_step` |
| **켤 때마다 배치를 초기화한다** | 시작하면 "플레이트만 있는 공장"이 된다. 직전 배치는 '이전 배치' 프리셋에 남는다 | 줄 7315~7338 |
| 앱 코어를 import 하면 파일을 쓴다 | 시작 코드가 공장 초기화 → 자동 저장을 하므로, 앱 코어를 불러오는 다른 스크립트도 `calib.json` 을 덮어쓴다 (9/24, 9/27 채점기 실행 때 블록 목록과 '이전 배치'가 바뀌었다) | 시작 코드 |
| `h_ft_save` 는 원자적 저장이 아니다 | 다른 저장은 임시 파일 → 바꿔치기인데, 이것만 파일에 바로 쓴다 | `h_ft_save` |

### 16-3. AI

| 문제 | 내용 |
|---|---|
| **실제 말에 약하다** | 합성 검증 98.5% 지만 실제 발화는 명령 86문장 중 최소 42%가 틀렸다. 학습 데이터가 전부 규칙 생성 문장이고, 검증셋도 같은 생성기에서 나왔다 (문장이 글자까지 같은 비율 24.5%) |
| **앱의 RACHEL 바이너리에 상한 버그** | `rachel_cpp/rachel` 은 200토큰에서 생성을 끊는다. 5단계 답(238자)이 잘려 5단계 **0/173**. 평가용 `rachel_eval`(상한 400)을 따로 만들었고 앱 바이너리는 그대로다 |
| **앱은 옛 가중치를 쓴다** | 앱이 여는 파일은 `rachel.bin` = v8. 정본은 `rachel_v9.bin` |
| 문맥 179자가 짧다 | 5단계 답 하나(최대 243자)도 통째로 못 담는다. 학습 예의 33.5%가 179자를 넘는다 (sliding window 로 이어서 생성은 된다) |
| 힌트의 물건 어휘가 4개뿐 | "빨간 거"처럼 부르면 도킹 색으로 오인한다 |
| Gemma 는 파인튜닝판이 아니다 | 앱이 쓰던 Gemma 는 원본이다. 파인튜닝한 것은 Gemma 3n 용 LoRA 이고 배포된 적이 없다 |
| 기본 엔진이 Gemma 쪽이다 | `auto` 는 Spark 가 살아 있으면 Gemma 원본을 쓴다. RACHEL 은 직접 골라야 돈다 |
| 시스템 전체는 결정론이 아니다 | RACHEL 자체는 같은 입력에 같은 출력이지만, 앞단의 음성 인식은 같은 말에도 결과가 다르다 |

### 16-4. 개발 관리
