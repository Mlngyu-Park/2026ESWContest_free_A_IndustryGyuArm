# RACHEL 을 만든 과정

색으로 말하면 로봇이 움직이는 것 — 그것 하나를 절대적으로 잘하는
모델을 직접 만들었다. 학습 데이터 만들기부터 C++ 추론 엔진까지 전부.

학습 세부는 [TRAINING.md](TRAINING.md) 에, 여기는 **왜 그렇게 했는지와
막힌 곳을 어떻게 뚫었는지**를 적는다.

---

## 0. 왜 직접 만들었나

Gemma 4 를 파인튜닝해 쓰고 있었다. 잘 됐지만 두 가지가 걸렸다.

- **Spark(DGX) 가 있어야 돌아간다.** 대회장에서 네트워크가 끊기면 끝이다.
- **한 문장에 1.3초.** "말하는 즉시 시뮬" 이 목표인데 체감이 안 맞았다.

그래서 색 명령만 하는 작은 모델을 직접 만들기로 했다.
범용성을 버리는 대신 그 하나를 확실하게, 그리고 노트북에서 돌게.

---

## 1. 문제를 어떻게 좁혔나

로봇 명령 전체를 배우게 하지 않았다. **말 → 블록 번역** 하나로 좁혔다.

```
입력:  보라=d2 빨강=d10 주황=d11 | 펜=초록@d2
       힌트 d2 d10
       보라색에 있는 초록색 펜 잡은 다음에 그거 빨간색으로 이동시켜줘
       >
출력:  {"blocks": ["@goto:d2", "@grasp:ppap", "@goto:d10", "@release:d10"]}
```

역기구학도, 경로 계획도, 충돌 검사도 모델이 하지 않는다.
그건 전부 앱이 계산으로 푼다. 모델은 **말을 블록으로 바꾸는 일만** 한다.

이 경계선이 프로젝트의 원칙이다 — AI 는 말→블록, 제어는 계산.

---

## 2. 데이터를 사람이 안 만들었다

15만 쌍을 규칙으로 합성했다 (`gen_data.py`).
사람이 라벨링한 데이터는 한 줄도 없다.

핵심은 **실제로 사람이 말하는 방식을 데이터에 넣은 것**이다.
전부 실사용 로그에서 관찰한 것들이다:

| 넣은 것 | 예 | 왜 |
|---|---|---|
| 색 지칭 70% | "빨간 도킹", "노란 데" | 색 명령이 주력 |
| STT 오염 | "도킹"→"토킹" | 음성 인식이 자주 틀림 |
| 군말 | "야", "어", "음" | 사람은 이렇게 말함 |
| 자기 정정 | "빨간 아 아니 보라" | 말하다 바꿈 — **마지막 말이 정답** |
| 호명 | "레이첼아 ~" | 이름을 부르고 명령함 |
| 거절 15% | 없는 색·번호 | 못 하는 건 못 한다고 해야 함 |

거절 데이터를 15% 나 넣은 이유가 있다. 없는 색을 시켰을 때
아무거나 지어내면 로봇이 엉뚱한 데로 간다. 실물이 움직이는 시스템에서는
**틀린 답보다 못 한다는 답이 낫다.**

---

## 3. 가장 크게 막혔던 곳

색 지칭 정확도가 **62.7%** 에서 안 올라갔다.

"보라색 도킹" 이라고 하면 장면표에서 보라=d2 를 찾아야 하는데,
색이 두세 개 나오면 자꾸 틀렸다.

세 번 시도했고 세 번 다 실패했다:

| 판 | 시도 | 결과 |
|---|---|---|
| v1 | 장면표를 그대로 줌 | 62.7% |
| v2 | 표 방향을 색=도킹 으로 뒤집음 | 65.2% |
| v3 | 조회 결과를 먼저 쓰게 시킴 (답안지 방식) | 64.0% |

v3 에서 깨달았다. **답안지를 먼저 쓰라고 했더니 답안지를 틀렸다.**
사전 찾기는 신경망이 잘하는 일이 아니다.

그래서 모델에서 빼고 **33줄짜리 전처리**로 옮겼다 (`hints.py`).
정규식으로 문장에서 색·번호를 순서대로 찾아 도킹 id 로 바꿔
입력에 "힌트" 로 붙여준다.

**62.7% → 99.6%.** 코드 33줄로 끝났다.

> 배운 것: 모델 크기나 학습량보다, **신경망에게 뭘 시키고 뭘 계산에
> 넘기느냐**가 성능을 결정한다. 사전 찾기처럼 계산이 완벽하게 하는 일은
> 절대 신경망에 시키지 않는다.

---

## 4. 실전에서 깨진 것

학습 정확도 99.6% 를 찍고 실제로 써봤더니 **첫날 출력이 깨졌다.**

내용은 맞는데 JSON 껍데기가 망가졌다. 원인은 어이없었다 —
**'야', '으' 두 글자가 학습 데이터에 없었다.**

글자 단위 토크나이저라 어휘에 없는 글자는 `<unk>` 가 되는데,
그게 문장 첫머리에 오니 모델이 흔들렸다. "야 빨간 도킹으로" 처럼
실제로는 아주 흔한 말인데 합성 데이터에는 없던 것이다.

그래서 만든 게 `test_real.py` — **실사용 회귀시험**이다.
쓰다가 틀린 문장을 그대로 보관해서, 새 판이 옛 문장을 다시 틀리면
통과가 안 된다. 실사용이 곧 시험 문제집이 됐다.

## 5. 완성된 모델

| 항목 | 값 |
|---|---|
| 구조 | GPT 디코더 (직접 구현, torch 기본 모듈만) |
| 파라미터 | 10.1M |
| 차원 / 층 / 헤드 | 320 / 8 / 8 |
| 문맥 | 256자 |
| 토크나이저 | 글자 단위 167자 |
| 학습 | AdamW, lr 3e-4, 배치 192, 8에폭 |
| 학습 시간 | 약 33분 (DGX Spark GB10 1장) |
| 정확도 | 완전 일치 99.6% |

손실을 `>` 뒤(답)에만 걸었다. 장면·명령을 외우는 데 용량을 쓰지 않게.

**학습만 GPU 를 쓰고 추론은 CPU 전용이다.** 노트북에서 돌아야 하니까.

## 6. 가볍게 만들기

### 6-1. int8 양자화 — 실패에서 배운 것

먼저 가중치와 활성값을 둘 다 int8 로 했다.
출력이 **"겨겨겨겨"** 같은 쓰레기가 나왔다.

작은 모델(320차원)은 활성값 분포가 좁아서 int8 로 뭉개면
정보가 다 날아간다. 그래서 **W8A32** 로 바꿨다 —
가중치만 int8, 활성값은 float32.

38MB → **19.5MB**, 정확도 유지.

### 6-2. C++ 로 다시 쓰기

파이썬 + torch 는 한 문장에 **1,265ms** 걸렸다.
torch 를 불러오는 것만으로도 무거웠다.

그래서 추론 엔진을 C++ 로 직접 짰다 (`rachel_cpp/rachel.cpp`, 307줄).
외부 라이브러리 없이 표준 C++ 만 썼다.

- KV 캐시 — 이미 계산한 토큰을 다시 안 함
- 가중치를 자체 형식(RCHL)으로 저장
- 실행 파일 **80KB**, 가중치 9.6MB

**1,265ms → 172ms (7.4배).**

### 6-3. OpenMP 를 뺐다

병렬화하려고 OpenMP 를 넣었더니 **4배 느려졌다** (168ms → 617~761ms).

모델이 작아서(320차원) 스레드를 만드는 비용이 계산보다 컸다.
행렬 하나가 너무 작아 나눌 가치가 없었다.

빼고 단일 스레드로 돌렸다. 코드에 이유를 주석으로 남겼다 —
나중에 누가 또 넣을까 봐.

### 6-4. 상주 모드

매번 실행하면 가중치 9.6MB 를 다시 읽는다.
프로세스를 띄워두고 표준입출력으로 문장만 주고받게 했다.

**172ms → 134ms** (측정 당시). 이 노트북에서 다시 재면 169ms 인데,
장비마다 다르다. 중요한 건 파이썬 1,265ms 대비 **7배 이상** 이라는 것.

## 7. 최종 성적

| | 크기 | 한 문장 | 정확도 |
|---|---|---|---|
| Gemma 4 E4B (Spark) | 4.3GB | 1,300ms | — |
| RACHEL 파이썬 (torch) | 38MB | 1,265ms | 99.6% |
| RACHEL int8 | 19.5MB | — | 99.6% |
| **RACHEL C++ (상주)** | **9.6MB** | **134~169ms** | **100%** (200/200) |

**Spark 없이 노트북에서 돌고, 10배 빠르고, 450배 작다.**

앱에서 AI 엔진을 골라 쓸 수 있게 해뒀다 —
C++ / 파이썬 / Gemma / 규칙 파서.

## 8. 중간에 틀렸던 것들

정직하게 남긴다. 이 과정에서 내가 놓쳤던 것들이다.

**속도를 좋은 것만 골라 보고했다.** "143ms" 라고 했는데 실제 로그를
보니 1,902ms 였다. 세 번 중 제일 빠른 것만 본 것이다.
이후로는 로그 전체 평균으로 본다.

**출력에 `{"` 가 빠졌다.** 프롬프트 끝에 `>` 를 안 붙여서
모델이 어디부터가 자기 몫인지 몰랐다.

**어휘 번호가 하나씩 밀렸다.** 어휘 파일을 `\n` 으로 이어 저장했는데
`\n` 자체가 어휘에 있어서 깨졌다. 길이를 앞에 붙이는 형식으로 바꿨다.

## 10. 이 과정에서 얻은 것

기술보다 **경계선을 어디에 긋느냐**가 중요했다.

- 사전 찾기를 계산으로 넘기니 62.7% → 99.6%
- 기구학을 앱에 맡기니 모델이 10M 로 충분했다
- OpenMP 를 빼니 4배 빨라졌다

셋 다 "더 하는 것" 이 아니라 **"덜 하는 것"** 으로 풀렸다.
AI 를 어디까지 쓸지 정하는 게, AI 를 잘 쓰는 것보다 먼저였다.
