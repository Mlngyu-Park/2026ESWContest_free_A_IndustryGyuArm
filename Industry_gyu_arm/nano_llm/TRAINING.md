# RACHEL 학습 정리

어떻게 데이터를 만들고, 어떤 구조를, 어떻게 학습시켰는지의 기록.
전 과정이 이 폴더 안의 코드로 재현된다.

## 1. 무엇을 배우게 하는가

입력(장면 + 힌트 + 명령)을 주면 블록 JSON 을 출력하는 번역 문제다.

```
입력:  보라=d2 빨강=d10 주황=d11 | 펜=초록@d2
       힌트 d2 d10
       보라색에 있는 초록색 펜 잡은 다음에 그거 빨간색으로 이동시켜줘
       >
출력:  {"blocks": ["@goto:d2", "@grasp:ppap", "@goto:d10", "@release:d10"]}
```

- 장면: 색↔도킹 배치는 매번 다르므로 입력으로 준다. 외우게 하지 않는다.
- 힌트: 문장 속 색·번호를 도킹 id 로 바꾼 것. **모델이 아니라 20줄짜리
  전처리(hints.py)가 만든다.** 사전 찾기는 계산이 완벽하게 하는 일이라
  신경망에 시키지 않는다 — 이 결정 하나가 정확도를 64% → 99.6% 로 올렸다.
- `>` 뒤가 모델의 몫. 학습 손실도 여기에만 건다.

## 2. 데이터 — gen_data.py

규칙 기반 합성 15만 쌍 (train 147,000 / val 3,000). 사람이 라벨링하지 않는다.

| 구성 | 비율 | 내용 |
|---|---|---|
| 잡아서 옮기기 | 30% | A의 펜을 B로 |
| 2단계 이송 | 27% | A→B 놓고 다시 B→C (시연 명령이라 최다 배정) |
| 잡기만 / 놓기만 | 15% | |
| 제자리·조작·속도 | 13% | 그리퍼·하강·정지·배속 |
| 거절 | 15% | 없는 색·번호, 할 수 없는 요청 → 빈 블록 |

말투 다양화 (전부 실사용 로그에서 관찰된 것):
- 색 지칭 70% ("빨간 도킹", "노란 데", "초록색 펜") — 색 명령이 주력이라서
- STT 오염: "도킹"→"토킹", 띄어쓰기 붕괴, 어미 변형
- 군말: "야", "어", "음" / 맺음말: "좀 해줘 봐", "부탁해"
- 자기 정정: "빨간 아 아니 보라 도킹" — 마지막 말이 정답
- 호명: "레이첼아 ~" 는 무시하고 명령만 처리
- 조사 변형: "~로/~으로"

## 3. 토크나이저 — tokenizer.py

글자 단위, 약 160자. 학습 데이터에 나온 글자를 모아 번호를 붙인 게 전부다.
어휘가 좁은 문제라 서브워드(BPE)가 필요 없고, 모르는 글자는 `<unk>` 처리.

주의: **어휘에 없는 글자는 실전에서 사고가 된다.** '야', '으' 두 글자가
학습 문장에 없어서 실사용 첫날 출력 형식이 깨졌다 (내용은 맞았는데 JSON
껍데기가 깨짐). 데이터에 해당 말투를 넣어 해결했다.

## 4. 모델 — model.py

GPT 구조 디코더 전용 트랜스포머. 직접 구현 (torch 기본 모듈만).

| 항목 | 값 |
|---|---|
| 파라미터 | 10.0M (파일 38MB) |
| 차원 / 층 / 헤드 | 320 / 8 / 8 |
| 문맥 길이 | 256자 |
| 출력 임베딩 | 입력과 가중치 공유 |
| 디코딩 | greedy (temperature 0) — 같은 입력 = 같은 출력 |

## 5. 학습 — train.py

| 항목 | 값 |
|---|---|
| 손실 | cross entropy, **`>` 뒤(답)에만** — 장면·명령 암기에 용량 안 씀 |
| 옵티마이저 | AdamW, lr 3e-4, weight decay 0.05, 코사인 감쇠 |
| 배치 / 에폭 | 192 / 8 |
| 정밀도 | bf16 autocast (GPU) |
| 시간 | 약 33분 (DGX Spark GB10 1장) |
| 선택 기준 | 에폭마다 검증 **완전 일치율**(생성 == 정답, 글자까지) 최고를 저장 |

추론은 CPU 전용이다. 학습만 GPU 를 쓴다.

## 6. 판올림 기록 — 뭐가 효과 있었고 뭐가 없었나

| 판 | 바꾼 것 | 색 지칭 | 교훈 |
|---|---|---|---|
| v1 | 기본 (모델이 장면표 조회) | 62.7% | 색 여러 개 조회가 병목 |
| v2 | 장면표를 색=도킹 방향으로 | 65.2% | 방향 문제가 아니었다 |
| v3 | 조회 결과를 먼저 쓰게 (답안지) | 64.0% | 답안지 자체를 틀림 — 조회는 신경망에 무리 |
| v4 | **조회를 전처리(hints.py)로 이관** | **99.6%** | 경계선을 옮기니 한 방에 해결 |
| v5 | 실사용 말버릇 (군말·정정·으로) | 99.6% | 실전 첫날 깨진 형식 교정 |
| v6 | "잡아서 …다시 잡아서" 2단계 말투 | — | "~한 다음" 단어가 아니라 목적지 개수로 구분하게 |

핵심 교훈 하나: **모델 크기나 학습량보다, 신경망에게 뭘 시키고 뭘 계산에
넘기느냐가 성능을 결정했다.** v1→v3 은 같은 자리를 맴돌았고 v4 는 코드
20줄로 끝났다.

## 7. 평가

- `analyze.py` — 검증셋을 명령 종류별(2단계/색지칭/거절…)로 나눠 채점.
  전체 평균에 숨는 약점을 찾는 용도 (v1 의 "색 62.7%" 를 이걸로 발견)
- `test_real.py` — **실사용 회귀시험.** 실제 사용 중 틀렸던 문장을 그대로
  보관해, 새 판이 옛 문장을 다시 틀리면 통과가 안 된다. 쓰다가 틀리는
  문장이 나오면 여기 추가한다 — 실사용이 곧 시험 문제집.
- 앱의 사용 기록(llm_usage.jsonl)이 다음 판의 데이터 재료가 된다.

## 8. 재현

```bash
python gen_data.py 150000     # train.jsonl / val.jsonl
python train.py               # rachel.pt (GPU 권장, 약 33분)
python analyze.py             # 종류별 채점
python test_real.py           # 실사용 회귀시험
python infer.py --bench       # 정확도 + 평균 지연
```
