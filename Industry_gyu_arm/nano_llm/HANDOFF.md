## 이미 만든 것 — RACHEL

**파인튜닝이 아니다. 랜덤 가중치에서 시작한 from scratch 모델이다.**

| 항목 | 값 |
|---|---|
| 하는 일 | 한국어 말 → 로봇 블록 JSON |
| 파라미터 | 10.1M |
| 구조 | GPT 디코더 (직접 구현, 48줄) |
| 차원/층/헤드/문맥 | 320 / 8 / 8 / 256 |
| 토크나이저 | 글자 단위 167자 |
| 학습 데이터 | 규칙 합성 15만 쌍 (사람 라벨링 0) |
| 학습 시간 | 33분 (DGX Spark GB10 1장) |
| 정확도 | 완전 일치 99.6% |
| 추론 | C++ 307줄 직접 구현, 168ms, 9.6MB |

## 이 방식의 핵심 3가지

새 모델을 만들 때도 **이 세 가지를 그대로 적용**하면 된다.
이건 이론이 아니라 실측으로 검증된 것이다.

### 1. 계산으로 되는 건 신경망에 안 시킨다 ← 가장 중요

RACHEL 에서 색→도킹 조회를 모델이 하게 했더니 **62.7%** 에서 안 올라갔다.
세 가지 방법을 시도했고 전부 실패했다 (62.7% → 65.2% → 64.0%).

그걸 **33줄짜리 정규식 전처리**(`hints.py`)로 빼냈더니 **99.6%** 가 됐다.

```python
# hints.py 가 하는 일 — 문장에서 색을 찾아 도킹 id 로 바꿔 입력에 붙인다
입력에 "힌트 d2 d10" 이 추가되고, 모델은 그 순서만 해석하면 된다
```

> **새 모델에서도 먼저 물을 것: "이 중에 사전 찾기나 규칙으로 되는 게 있나?"**
> 있으면 전부 빼내라. 모델은 언어 구조 판단만 하게.

### 2. 데이터는 규칙으로 합성한다

사람이 라벨링하지 않는다. `gen_data.py` 가 15만 쌍을 만든다.

중요한 건 **실제 말투를 넣는 것**이다. 깨끗한 문장만 학습하면 실전에서 깨진다:

```python
COLORS = ["빨강", "주황", "노랑", "초록", "파랑", "보라"]

def stt_noise(t):    # "도킹" -> "토킹" 같은 음성인식 오류
def vocative(t):     # "레이첼아 ~" 호명
# 자기 정정: "빨간 아 아니 보라" (마지막 말이 정답)
# 군말: "야", "어", "음"
# 거절 15%: 없는 색 시키면 빈 블록
```

**거절 데이터를 꼭 넣을 것.** 실물이 움직이는 시스템에서는
틀린 답보다 "못 한다"는 답이 낫다.

### 3. 손실은 답 부분에만 건다

입력(장면·명령)을 외우는 데 용량을 쓰지 않게 한다.
`>` 다음부터가 모델의 몫이고, cross entropy 를 거기에만 건다.

```python
# train.py
x = (ids + ans)[:CTX]
loss_from = min(len(ids), CTX)    # 여기부터 손실 계산
```

## 실패에서 배운 것 (같은 실수 반복 금지)

| 실패 | 원인 | 해결 |
|---|---|---|
| 출력이 "겨겨겨겨" | 활성값까지 int8 로 양자화 | **W8A32** (가중치만 int8) |
| 첫날 출력 형식 깨짐 | '야','으' 가 어휘에 없었음 | 데이터에 그 말투 추가 + 회귀시험 |
| OpenMP 넣으니 4배 느려짐 | 모델이 작아 스레드 비용 > 계산 | 단일 스레드 |
| 출력에 `{"` 빠짐 | 프롬프트에 `>` 종결자 없음 | `>` 추가 |
| 어휘 번호 하나씩 밀림 | `\n` 으로 이어 저장했는데 `\n` 이 어휘에 있음 | 길이 접두 형식 |

## 새 모델 만들 때 절차

1. **문제 좁히기** — "이 모델이 딱 하나 잘해야 하는 게 뭔가?"
   범용성을 버릴수록 작은 모델로 높은 정확도가 나온다.

2. **경계선 긋기** — 그 일 중에 규칙·사전으로 되는 부분을 전부 빼낸다.
   (RACHEL 은 이걸로 62.7% → 99.6%)

3. **입출력 형식 정하기** — 입력 끝에 `>` 같은 종결자를 반드시 넣는다.

4. **`gen_data.py` 를 새 문제에 맞게 고쳐 쓴다**
   실제 사용자가 어떻게 말할지(오타·군말·정정)를 넣고, 거절 데이터도 넣는다.

5. **`model.py`, `train.py`, `tokenizer.py` 는 거의 그대로 재사용**
   어휘 크기와 문맥 길이만 새 문제에 맞게.

6. **학습은 Spark 에서** (사용자 PC 금지)

7. **`analyze.py` 로 종류별 채점** — 전체 평균에 숨는 약점을 찾는다.
   RACHEL 은 이걸로 "색 지칭만 62.7%" 를 발견했다.

8. **실전 투입 후 틀린 문장을 `test_real.py` 에 추가** — 실사용이 시험 문제집

9. **C++ 엔진은 `rachel.cpp` 를 고쳐 쓴다** (구조가 같으면 거의 그대로)

- 그 모델이 딱 하나 잘해야 하는 일이 무엇인지
- 입력과 출력이 무엇인지 (예시 한두 개)
- 그 일 중 규칙으로 되는 부분이 있는지

그 답을 듣고 나서 위 절차대로 진행하면 된다.
